# 漫画 · 第 69 话 性能预算与 CI 门禁

> 对应正文：[docs/quality/03-performance-budget.md](../../docs/quality/03-performance-budget.md) ｜ 原画：[EP.69-performance-budget.svg](./EP.69-performance-budget.svg)

## 登场角色

- **标签君**：结构师。本话他发现内容站 LCP 从 2.1s 恶化到 4.3s，而 PR 全绿。
- **码叔**：老工程师。他主张把「可接受的最差体验」写成预算，接到 CI 上。

## 剧情梗概

排查发现首屏 JS 从 160KB 涨到 340KB：依赖升级引入整包 lodash，图表库同步加载进首屏。团队此前只看线上指标，发现时已过两周。码叔建立三层预算（资源、请求、指标），构建后统计 chunk 体积，超预算阻断合并；图表库改动态 `import()`，lodash 改按需导入。首屏 JS 回落到 165KB，LCP 回到 2.2s。

## 分格解读

### 格1 · 痛点现场

没有预算时，「变慢」是一个只能靠感觉和线上告警发现的问题。PR 里看不到体积变化，评审也无法判断一次依赖升级的代价。等指标恶化再排查，已经浪费了两周。

### 格2 · 机制登场

三层预算各有职责：资源预算约束交付物，请求预算约束连接成本，指标预算约束用户感受。资源与请求是可归因的输入，指标是最终输出。只定指标，超支时不知道是谁超的；只定资源，可能省了字节却仍然慢。

### 格3 · 落地收束

码叔把预算写进仓库，CI 固定设备与网络档位，构建后统计 chunk 并贴 PR 评论；门禁分级——小幅超支告警，显著超支阻断。示例里拖动 JS 体积滑块可以观察预算判定，点击「实测长任务」则用 `PerformanceObserver('longtask')` 验证超过 50ms 的任务会阻塞输入。

## 码叔划重点

1. 三层预算成组落地：资源、请求、指标，单看一层会漏。
2. 单位与口径写清：压缩前 / 后、KB / KiB、实验室 / 现场。
3. 用 P75 定目标，不要用平均值或拍脑袋的极限值。
4. 分级门禁：小幅告警、显著阻断，保留合理弹性。
5. 输出变化量与归因模块，比一个红叉更有行动力。
6. 预算要定期复查，过期预算会逼团队绕过门禁。

## 自测一题

**问**：既然已经有线上 RUM 指标，为什么还要在 CI 里做体积预算？

**答**：RUM 是事后证据，反馈周期以天计；体积预算是事前约束，在合入前就能拦住回退。两者互补：预算负责「不让问题进线上」，RUM 负责「验证真实用户是否真的变好」。只有 RUM 没有预算，团队每次都要等线上恶化才行动。
