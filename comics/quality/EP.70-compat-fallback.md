# 漫画 · 第 70 话 兼容矩阵与渐进增强兜底

> 对应正文：[docs/quality/04-compat-fallback.md](../../docs/quality/04-compat-fallback.md) ｜ 原画：[EP.70-compat-fallback.svg](./EP.70-compat-fallback.svg)

## 登场角色

- **像素酱**：CSS 造型师。她用 `:has()` 做了「有图两列」卡片，觉得代码又短又优雅。
- **标签君**：结构师。灰度到旧版 Safari 后，他接到一整页布局错乱的告警。

## 剧情梗概

增强样式直接写在基础规则里，旧引擎不支持 `:has()` 时整段规则失效，卡片全部退回错位布局。标签君把基础层改成单列，把 `:has()` 分支放进 `@supports`，并给 popover 菜单补了 `hidden` + 显隐类的兜底。两人还建立了兼容矩阵，标注每个特性的状态、使用位置、兜底方案与负责人。

## 分格解读

### 格1 · 痛点现场

问题不在 `:has()` 本身，而在它的位置。增强能力一旦写进基础路径，旧环境不是「体验差一点」，而是「布局直接坏掉」。没有兼容矩阵时，评审也没人确认这个特性到底能不能直接用。

### 格2 · 机制登场

渐进增强要求能力分层：基础层用语义 HTML 与普通 CSS 保证任务可完成；增强层用 `@supports` 或 `in` 检测叠加现代能力；兜底层提供等价路径。检测能力而不是 UA——UA 会伪装、会过期，`CSS.supports('selector(:has(*))')` 才可靠。

### 格3 · 落地收束

标签君把基础布局改为单列，`:has()` 两列放进 `@supports`；菜单在支持 popover 时顶层渲染，不支持时用 `hidden` 与 `aria-expanded` 管理；每个增强组件都加一条「强制降级」用例。示例里的「模拟不支持」开关就是这条用例的现场版：关掉增强后，功能仍然完整。

## 码叔划重点

1. 主任务必须在无 JS / 旧引擎下可完成，再谈增强。
2. 检测能力不检测 UA，`@supports` 与 `in` 更可靠。
3. 增强样式必须放进 `@supports`，不能混进基础规则。
4. 兜底要可测试，提供强制降级开关或用例。
5. 兼容矩阵要标注状态、位置、兜底与负责人。
6. 不要为长尾过度兜底，按用户占比与任务重要性取舍。

## 自测一题

**问**：为什么 `@supports` 里只放增强样式，基础样式要写在检测之外？

**答**：`@supports` 的作用是「条件满足才应用」。如果把基础布局也放进去，不支持时整段规则都不生效，页面就没有布局了。正确写法是基础规则在外、增强规则在 `@supports` 内，这样不支持的环境拿到的是朴素但完整的布局，支持的环境再升级。
