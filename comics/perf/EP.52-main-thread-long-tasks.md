# 漫画 · 第 52 话 主线程与长任务治理

## 登场角色

- **像素酱**：CSS 造型师，本话主角。兴冲冲加了"一键导出 80 万行"，点下去页面直接白屏，输入框打字半天不回显。
- **标签君**：结构师，把事件循环画成三条泳道，解释什么叫长任务、切片和 Worker。

## 剧情梗概

导出按钮写了一个同步 `for` 循环，80 万行一次跑完，主线程被锁 1.2 秒。用户看到白屏、输入无响应，甚至以为页面崩了。像素酱以为"数据太大没办法"，标签君说：数据没变，变的是任务——把它切成可中断的小块，或者干脆搬去 Worker，主线程就能继续响应。

## 分格解读

### 格1 · 痛点现场

一次点击触发一个 1.2s 的同步任务：进度条停在 0%，输入框的字符要等任务结束才出现。主线程同一时间只能做一件事，渲染、事件处理、脚本执行都排在它后面。用户感知到的不是"导出慢"，而是"整个页面死了"——白屏只是表象，长任务才是根因。

### 格2 · 机制登场

浏览器把超过 50ms 的任务标记为长任务。三条退路：① 切片，把大循环按 20ms 左右一段拆开，每片结束调用 `await scheduler.yield()` 或 `setTimeout(0)` 让出主线程，让输入和绘制的回调插进来；② 协作式让出，让进度条每片都更新一次；③ 计算搬进 Web Worker，纯数据转换不碰 DOM，主线程只负责收发消息与渲染。图上三条泳道对比：一整块红条、一排小绿块、以及 Worker 与主线程并行。

### 格3 · 落地收束

导出面板的进度条从 0 平滑走到 100%，12 个切片、8.6 秒完成，期间可取消、可滚动；INP 从 620ms 降到 90ms，输入回显从 1.2s 降到 0.1s。注意总耗时并没有魔法般变短，改变的是"等待的形态"：用户始终能操作，进度始终在动，长任务被拆成了不会阻塞交互的小块。

## 码叔划重点

1. 超过 50ms 就是长任务：输入、点击、滚动都只能排队等它结束。
2. 切片的关键是可中断：每片留 `yield`，让浏览器有机会处理交互与绘制。
3. 纯计算进 Worker：DOM 只留在主线程，别在 Worker 里碰页面。

## 自测一题

**问**：把同步循环改成 `setTimeout(fn, 0)` 递归切片后，总耗时反而变长了，这样优化值得吗？

**答**：值得，但要分清指标。切片会增加调度开销，总墙钟时间可能上升；收益在 INP、输入回显和进度反馈——用户不再觉得页面卡死。判断标准应是交互延迟与可取消性，而非单纯总时长。如果计算量大且无需 DOM，优先搬进 Worker，主线程几乎零占用；切片适合必须操作 DOM 或需要频繁汇报进度的场景。
