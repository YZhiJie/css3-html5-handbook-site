## 登场角色

- **像素酱**：CSS 造型师，本话主角。发布后盯着手机看，屏幕上只剩一个转圈的小光标，三秒后内容才突然出现。
- **标签君**：结构师，把关键渲染路径拆成四个方块，指出到底是谁挡住了首屏。

## 剧情梗概

用户点开页面，看到的是 3.2 秒纯白。像素酱原以为只是"网络慢"，标签君打开网络面板：首包 JS 3.2MB、12 个阻塞 CSS、字体 3 秒未到导致文字隐身。三个都跟首屏无关，却都排在首屏前面。标签君：先把关键路径让出来，再谈体验。

## 分格解读

### 格1 · 痛点现场

三宗罪各有分工：巨包 JS 下载完还要解析编译，主线程被占满；多个 `link rel="stylesheet"` 串行阻塞，浏览器必须等 CSSOM 才敢渲染；`font-display` 缺省时的 FOIT 会让文字在字体到达前完全不可见。共同结果就是白屏——不是"加载慢"，而是关键渲染路径被非关键资源占满。

### 格2 · 机制登场

关键渲染路径是 HTML → CSSOM → 渲染树 → 首次绘制。图上 HTML 0.3s、CSS 1.2s、JS 2.4s，合计把 FCP 推到 3.9s。治理三招：① 骨架屏，用结构占位先给出视觉反馈，接口慢或失败都有兜底；② `font-display: swap`，先用系统字体渲染，字体到达再替换，配合 `size-adjust` 等度量匹配减少跳动；③ 资源提示，`preload` 关键 CSS/首屏图，`preconnect` 提前建连字体域，非关键资源 `defer`/`async` 或干脆挪到交互后。

### 格3 · 落地收束

优化后时间线整段左移：HTML 0.2s、CSS 0.3s、首屏 JS 0.4s，FCP 从 3.9s 降到 1.1s，骨架首帧 0.6s、LCP 1.4s。注意最后一小段 IDLE 不是浪费，而是留给主线程喘息的余量。先看见结构，再看见内容，最后才是完整——这个顺序比总时长更重要。

## 码叔划重点

1. 首屏只竞争关键资源：HTML、关键 CSS、首屏 JS，其余延后或按需加载。
2. 骨架屏先给结构，慢接口与失败都要有兜底，白屏不能是终点。
3. 字体三件套：`font-display: swap`、预加载、度量匹配，既要不挡字也要少跳动。

## 自测一题

**问**：把首屏 JS 从 3.2MB 压到 800KB 后，FCP 只从 3.9s 降到 3.5s，为什么收益这么小？

**答**：说明瓶颈不在 JS 体积，而在关键路径的串行等待。常见原因：CSS 仍在阻塞、字体仍走 FOIT、JS 虽小但放在 `<head>` 同步执行、或首屏请求受 TCP/TLS 建连限制。应该用瀑布图看"谁在等谁"，先并行化与提前加载，再谈减体积；同时确认 FCP 的触发条件是否被骨架屏或占位图提前满足。
