## 登场角色

- **像素酱**：CSS 造型师，本话主角。自信页面"看着挺快"，一上仪表盘三座全部亮红，才发现体感和指标是两回事。
- **标签君**：结构师，负责把 PerformanceObserver 采集、p75 聚合、预算看板这条链路摆清楚。

## 剧情梗概

像素酱改完一版页面，拍胸脯说"顺滑得很"。标签君默默打开生产环境的 RUM 看板：LCP 4.8s、INP 620ms、CLS 0.34，三座仪表全红。更扎心的是同一个人刷新三次，三个数字都不重样。标签君说：性能不是感觉，是分布——先学会量，再谈优化。

## 分格解读

### 格1 · 痛点现场

三座仪表分别对应 Web Vitals 的核心三指标：LCP 衡量最大内容块出现的时刻，4.8s 意味着首屏主视觉迟迟不出现；INP 衡量每次交互到下一帧绘制的延迟，620ms 让点击像按在棉花上；CLS 衡量布局偏移，0.34 说明图片、广告位在加载中反复"跳"。三者共同点：都只能在真实设备、真实网络下才有意义，本地开发机上常常一片绿。

### 格2 · 机制登场

度量链路分三步：① 用 `PerformanceObserver` 订阅 `largest-contentful-paint`、`event`（或 `first-input`）、`layout-shift` 等条目，并带 `buffered: true` 补收早于脚本执行的记录；② 把原始条目按页面、设备、网络分桶，取 **p75**（第 75 百分位）而不是平均值，避免少量极慢用户被平均掉；③ 把 p75 与阈值（LCP ≤ 2.5s、INP ≤ 200ms、CLS ≤ 0.1）对照，落到预算看板。注意 Lab（Lighthouse）可复现、可进 CI，Field（RUM）才是真实用户，二者互补。

### 格3 · 落地收束

看板把"实测 ÷ 预算"归一成柱长：LCP 2.1s / 2.5s 达标，INP 340ms / 200ms 越线变红，CLS 0.08 / 0.1 达标。右侧是 CI 门禁：PR 构建跑 Lighthouse，超预算阻断合并；线上 p75 越线触发告警。一格只盯三指标，异常再下钻到页面与设备分桶——先有可报警的数字，才有资格谈优化。

## 码叔划重点

1. 三指标阈值记牢：LCP ≤ 2.5s、INP ≤ 200ms、CLS ≤ 0.1，统一看 p75。
2. Lab 与 Field 互补：Lighthouse 管可复现与 CI，RUM 管真实用户分布。
3. 聚合看 p75 不看均值，均值会被少数极慢用户或极快缓存用户骗过去。

## 自测一题

**问**：团队用平均 LCP 汇报，数字一直 1.8s 很漂亮，但客服仍收到"打开很慢"的投诉，问题可能出在哪？

**答**：平均值被大量缓存命中、网络好的用户拉低了。少数弱网、低端机用户可能 LCP 超过 5s，但在均值里只占很小权重。应该按 p75（甚至 p90）分设备、分网络聚合，并检查是否有地区或机型长尾；均值只适合看整体趋势，不适合做达标判断。
