资源缓存与分发优化：从 HTTP 缓存到 Service Worker ​

面向前端开发人员的性能优化参考资料 —— 缓存不是"加个 max-age"，而是一套分层决策：浏览器 HTTP 缓存、CDN 边缘缓存、Service Worker 运行时缓存各自解决不同问题。本章把 Cache-Control、ETag、Vary、Age 这些响应头讲透，再串起带 hash 的静态资源长缓存、CDN 回源、SW 三大策略、版本化清理、Navigation Preload，以及压缩、图片格式、字体子集化、代码分包与资源提示的边界——最后给出一张"什么资源用什么策略"的决策表。

1. 概念解释 ​

1.1 缓存的三个层级 ​

一次页面请求最多会经过三层缓存，每一层都独立判断、独立失效：

层级位置谁在判断主要字段典型收益
浏览器 HTTP 缓存用户本地磁盘/内存浏览器Cache-Control、ETag、Last-Modified二次访问零请求、304 只回头部
CDN 边缘缓存离用户最近的节点CDNs-maxage、Surrogate-Control、Age、缓存键回源率下降、跨地域 RTT 缩短
Service Worker浏览器内的脚本代理你的代码CacheStorage、版本号、策略函数离线可用、策略可编程、秒开

关键认知：SW 缓存不会自动跟着 HTTP 缓存走。一个响应即使被 HTTP 缓存标记为 no-store，只要在 fetch 事件里 cache.put()，它依然会进 CacheStorage。三层都要显式设计。

1.2 HTTP 缓存字段逐个拆解 ​

指令 / 字段语义常见误区
max-age=31536000响应在 1 年内无需再验证（相对收到响应的时刻）对 HTML 用长 max-age 会导致发版后用户长期拿旧页面
s-maxage=600仅对共享缓存（CDN/代理）生效，优先级高于 max-age以为它也会缩短浏览器缓存
no-cache可以存，但每次复用前必须回源验证（走 ETag/304）误以为"完全不缓存"
no-store完全不许存，浏览器与中间代理都不能落盘对 HTML 滥用，失去 304 带来的带宽收益
private只允许浏览器私有缓存，CDN 不得缓存带用户信息的接口漏写 private 被 CDN 缓存串号
immutable在 max-age 内连刷新都不回源验证只对内容永不变化的 URL（带 hash）使用
stale-while-revalidate=60过期后 60 秒内先返回旧副本，同时后台更新只应作用于可容忍短暂旧数据的资源
Vary: Accept-Encoding缓存键加入请求头维度，压缩/非压缩各存一份漏写导致给不支持 Brotli 的客户端发 .br
Vary: *永不命中缓存（等价禁用）误用导致 CDN 命中率归零
Age响应自生成/验证以来经过的秒数（由缓存或 CDN 写入）把它当成业务时间或忽略 CDN 已缓存的时长

no-cache vs no-store 一句话：no-cache 是"先问再用的缓存"，no-store 是"根本不缓存"。HTML 入口页通常用 no-cache（保留 304 协商），登录态/一次性验证码接口用 no-store。

max-age 与 s-maxage：s-maxage 只影响 CDN；CDN 回源时给浏览器的响应仍按 max-age。典型组合是 HTML：Cache-Control: public, max-age=0, s-maxage=60, stale-while-revalidate=30——浏览器每次验证，CDN 边缘扛 60 秒。

Vary 是缓存键的一部分：Vary: Accept-Encoding 让 gzip 与 br 版本分开存；Vary: Cookie 几乎等于禁用 CDN 缓存（每个用户一份）。移动端/桌面端用同一 URL 返回不同内容时，应改 URL（如 ?v=m）而不是滥用 Vary: User-Agent。

1.3 带 hash 的静态资源长缓存，HTML 不缓存 ​

现代构建产物形如 app.9f3c2a1b.js：内容变 → hash 变 → URL 变，因此可以放心：

Cache-Control: public, max-age=31536000, immutable

而 index.html 的 URL 永远不变，必须保证用户能拿到最新引用：

Cache-Control: no-cache

这一对组合是 SPA/SSR 站点缓存设计的基石。唯一要小心的是"发布原子性"：新旧 HTML 与新旧 chunk 必须同时可用，至少保留上一版本产物一段时间，否则正在浏览的用户点进旧页面会 404。

1.4 CDN 边缘缓存与回源 ​

CDN 的缓存键通常由 host + path + query（可配置忽略部分 query）与 Vary 组成。几个工程要点：

  1. 回源收敛：边缘未命中才回源；s-maxage 决定边缘 TTL，stale-while-revalidate 让边缘在后台刷新时继续服务旧副本。
  2. 主动刷新：发版时对 HTML 与入口 JSON 调 purge API；带 hash 的资源无需刷新（URL 已变）。
  3. 命中率看两个数：边缘命中率（edge hit ratio）与回源带宽。命中率低先查 Vary、Cookie 透传、query 噪声。
  4. Age 判断新鲜度：边缘返回 Age: 42 表示这份响应已缓存 42 秒；Age 接近 s-maxage 时说明即将回源。

1.5 Service Worker：三策略、版本化与预加载 ​

SW 是"可编程的 HTTP 缓存"，三种基础策略与 HTTP 字段的对应关系：

SW 策略行为等价 HTTP 语义适用
Cache First命中缓存立即返回，未命中才走网络并写入长 max-age + immutable带 hash 的 JS/CSS、图片、字体
Network First先网络，成功写缓存，失败回退缓存no-cache + 离线兜底API、实时数据、HTML
Stale While Revalidate立即返回缓存，同时后台请求并更新stale-while-revalidate列表页数据、头像、非关键接口

版本化缓存清理：缓存名带构建版本（app-v2026.10.31），activate 时删除不匹配的旧缓存；不要在 install 里无条件 skipWaiting()，否则旧页面可能加载到新版 chunk 造成白屏（见 Service Worker 缓存策略）。

Navigation Preload：SW 启动本身有延迟，导航请求在 SW 唤醒前无法发网络请求。navigationPreload.enable() 让浏览器并行发起导航请求，SW 里 event.preloadResponse 拿到它，Network First 的 HTML 导航可少等几十到几百毫秒。

2. 语法说明 ​

2.1 一套可直接抄的响应头 ​

http
# 1) HTML 入口：每次协商，CDN 短缓存
Cache-Control: no-cache, public, s-maxage=60, stale-while-revalidate=30
ETag: "html-20261031-a"

# 2) 带 hash 的 JS/CSS：一年长缓存
Cache-Control: public, max-age=31536000, immutable
ETag: "js-9f3c2a1b"

# 3) 图片/字体（带 hash 或内容稳定）
Cache-Control: public, max-age=31536000, immutable
Vary: Accept-Encoding

# 4) 用户私有 API：不落共享缓存
Cache-Control: private, no-store

2.2 协商缓存：ETag / Last-Modified ​

http
# 首次响应
ETag: "v1-abc"
Last-Modified: Wed, 28 Oct 2026 08:00:00 GMT

# 再次请求（浏览器自动带）→ 未变化返回 304，无响应体
If-None-Match: "v1-abc"
If-Modified-Since: Wed, 28 Oct 2026 08:00:00 GMT
HTTP/1.1 304 Not Modified

ETag 优先于 Last-Modified：后者只有秒级精度，且"文件时间变了但内容没变"会误判。强 ETag 要求字节级一致；弱 ETag（W/"..."）允许语义等价。

2.3 SW 三策略的最小实现 ​

js
// sw.js —— 按资源类型分流
self.addEventListener('fetch', (event) => {
  const url = new URL(event.request.url);
  if (event.request.method !== 'GET') return;

  // 带 hash 的静态资源：Cache First
  if (/\.(js|css|woff2|png|jpg|avif|webp)$/.test(url.pathname)) {
    event.respondWith(
      caches.match(event.request).then((cached) =>
        cached || fetch(event.request).then((resp) => {
          const copy = resp.clone();
          caches.open('static-v3').then((c) => c.put(event.request, copy));
          return resp;
        })
      )
    );
    return;
  }

  // API：Network First + 超时兜底
  if (url.pathname.startsWith('/api/')) {
    event.respondWith(
      fetch(event.request)
        .then((resp) => {
          const copy = resp.clone();
          caches.open('api-v3').then((c) => c.put(event.request, copy));
          return resp;
        })
        .catch(() => caches.match(event.request))
    );
    return;
  }

  // 其余：Stale While Revalidate
  event.respondWith(
    caches.match(event.request).then((cached) => {
      const network = fetch(event.request).then((resp) => {
        const copy = resp.clone();
        caches.open('runtime-v3').then((c) => c.put(event.request, copy));
        return resp;
      });
      return cached || network;
    })
  );
});

2.4 版本化清理与 Navigation Preload ​

js
const CACHE_VERSION = 'v2026.10.31';
const KEEP = [`static-${CACHE_VERSION}`, `api-${CACHE_VERSION}`, `runtime-${CACHE_VERSION}`];

self.addEventListener('activate', (event) => {
  event.waitUntil((async () => {
    // 1) 打开导航预加载（让导航请求与 SW 启动并行）
    if (self.registration.navigationPreload) {
      await self.registration.navigationPreload.enable();
    }
    // 2) 删除不属于当前版本的缓存
    const names = await caches.keys();
    await Promise.all(
      names.filter((n) => !KEEP.includes(n)).map((n) => caches.delete(n))
    );
    // 3) 接管未受控页面（配合 skipWaiting 时使用）
    await self.clients.claim();
  })());
});

// 导航请求里消费预加载响应
self.addEventListener('fetch', (event) => {
  if (event.request.mode === 'navigate') {
    event.respondWith((async () => {
      try {
        const preload = await event.preloadResponse;
        if (preload) return preload;
        return await fetch(event.request);
      } catch {
        return (await caches.match('/offline.html')) || Response.error();
      }
    })());
  }
});

2.6 字体子集化与加载 ​

css
/* 按 unicode-range 切片：浏览器只下载页面实际用到的字集 */
@font-face {
  font-family: "Brand Sans";
  src: url("/fonts/brand-cjk.woff2") format("woff2");
  unicode-range: U+4E00-9FFF;      /* 中文主区；拉丁/标点另切片 */
  font-display: swap;
}

字体 preload 必须带 crossorigin（字体按 CORS 模式获取，漏写会重复下载）。font-display: swap 先显示回退字体，避免文字不可见（FOIT），代价是可能的字体切换（FOUT）。

2.7 资源提示与代码分包的边界 ​

手段解决什么不该做什么
tree-shaking删除未引用的 ESM 导出对 CommonJS/副作用不明的包期望过高；需 sideEffects: false 配合
路由分包首屏不加载其他路由代码拆得过碎导致大量小请求与瀑布
preload当前页确定要用的关键资源提前拉预加载未使用资源 → Console 警告 + 抢带宽
prefetch下一页可能用的资源低优先级预取移动端无节制预取，浪费流量与电量
modulepreload预取并解析编译 ESM 模块链对非模块脚本无效；仍要遵守优先级
preconnect提前 DNS+TCP+TLS超过 3~4 个关键域会反噬连接池

判断顺序：先问"这个资源首屏是否必需"——必需 → preload/高 fetchpriority；下一页高概率 → prefetch；只是第三方域预热 → preconnect/dns-prefetch。资源提示只调整时机，不会减少字节数；体积优化仍要靠压缩、分包与格式。

4. 使用场景示例 ​

4.1 场景一：SPA 发版后的"旧页面 + 新资源" ​

问题：用户停留在旧页面，发版后新请求命中新 CDN，旧 chunk 已被清理 → 动态 import() 404，页面白屏。

js
// 构建侧：产物按版本分目录，至少保留两个版本（上一版给在线用户）
// dist/2026.10.31/app.9f3c2a1b.js · dist/2026.10.24/app.8e2b1a0c.js

// 前端侧：捕获 chunk 加载失败，页面内提示刷新而不是崩溃
window.addEventListener('vite:preloadError', () => {
  document.querySelector('#update-tip')?.removeAttribute('hidden');
});

关键点：HTML 用 no-cache 保证下次刷新拿到新引用；带 hash 资源 immutable 长缓存；旧版本产物保留一个发布周期。示例页的"发版后"时间线可直观看到旧缓存失效与新 hash 请求。

4.2 场景二：CDN + SW 协同的新闻站 ​

js
// HTML：no-cache + 短 s-maxage；SW Network First 带 3 秒超时兜底
function networkFirstWithTimeout(request, timeoutMs = 3000) {
  const fromCache = caches.match(request);
  const timeout = new Promise((_, reject) => setTimeout(reject, timeoutMs));
  return Promise.race([
    fetch(request).then((resp) => {
      caches.open('news-v3').then((c) => c.put(request, resp.clone()));
      return resp;
    }),
    timeout
  ]).catch(() => fromCache.then((cached) => cached || Promise.reject(new Error('offline'))));
}

效果：网络正常时拿到最新文章；弱网 3 秒内未返回则读缓存，页面不空等。与 资源提示与 LCP/CLS 案例 配合，首屏主图与字体提前加载，HTML 仍保持可验证。

5. 实际应用案例分析 ​

5.1 某内容站：CDN 命中率从 41% 提到 92% ​

背景：日活 80 万的资讯站，CDN 边缘命中率长期 41%，回源带宽成本高。

排查：

  1. Cookie 透传：CDN 默认把 Cookie 纳入缓存键，每个登录用户一份缓存 → 命中率天然低。改为仅对匿名 HTML 与静态资源忽略 Cookie，登录态接口走 private。
  2. query 噪声与 Vary 写错：埋点参数被计入缓存键；Vary: User-Agent 让 UA 组合几乎无限。配置忽略 utm_*/fbclid，移动端改独立 URL。
  3. HTML TTL 太短：s-maxage=0 导致每次回源。调成 s-maxage=60, stale-while-revalidate=30，发版走 purge。

结果：命中率 92%，回源带宽下降约 65%，P95 TTFB 从 480ms 降到 120ms。结论：缓存问题 80% 出在缓存键，而不是 TTL 本身。

5.2 某电商 App：SW 版本化引发的白屏事故 ​

背景：PWA 改造后高峰期出现"打开白屏、刷新恢复"的投诉。

根因链：

  1. 新 SW 在 install 里直接 skipWaiting()，旧页面被新 SW 接管；
  2. 旧页面请求旧 chunk，而新 SW 的预缓存清单只含新 chunk；
  3. Cache First 未命中 → 回源 404（旧产物已清理）→ 动态 import 抛错 → 白屏。

修复：

  1. skipWaiting 改为"用户确认后更新"或延迟到下一次导航；
  2. 预缓存清单同时保留上一版本 chunk 一个发布周期；
  3. fetch 对 mode === 'navigate' 走 Network First，加离线兜底页，并监听 chunk 加载失败提示刷新。

结果：白屏投诉归零，SW 更新后首次加载成功率 99.6%。SW 生命周期细节见 Service Worker 缓存策略。

5.3 某后台系统：Brotli + 字体子集化 + 路由分包 ​

背景：中后台首屏 JS 1.8MB（未压缩），中文字体 3.2MB，弱网首屏 9 秒。

措施：

  1. Brotli 静态预压缩：构建时生成 .br 与 .gz，Nginx brotli_static on；JS 从 1.8MB → Brotli 约 420KB（文本压缩比随内容波动）。
  2. 路由分包 + 预取：首屏只加载登录与工作台，其余路由动态 import()；空闲时 requestIdleCallback 预取高频路由。
  3. 字体子集化 + LCP 图：中文按 unicode-range 切成 6 片，常用字只下载约 180KB；LCP 图用 AVIF + fetchpriority="high" + 宽高防 CLS。

结果：弱网首屏 9s → 3.1s，LCP 从 5.2s 降到 2.3s。注意：Brotli 对已压缩格式（JPEG/PNG/WebP/字体）几乎无收益，别对图片开 Brotli。

6. 最佳实践与常见坑 ​

6.1 十条必须遵守的规则 ​

  1. HTML 永不长缓存：入口页用 no-cache（保留 ETag 协商），配合 CDN 短 s-maxage 与发版 purge；长缓存 HTML 是"发版不生效"的头号原因。
  2. 带 hash 资源才配 immutable：URL 与内容绑定是长缓存的前提；不带 hash 的文件请用 no-cache 或短 TTL。
  3. no-cache ≠ 不缓存：需要"每次验证"用 no-cache，需要"绝不落盘"用 no-store；登录态接口用后者并加 private。
  4. s-maxage 只给 CDN 看：想同时控制浏览器与边缘，写 max-age=0, s-maxage=60；别指望 s-maxage 影响本地缓存。
  5. Vary 只写必要维度：Accept-Encoding 必写；User-Agent/Cookie 几乎等于禁用缓存，改用独立 URL 或登录态分流。
  6. 发版保留上一版本产物：新旧 HTML 与 chunk 的交叉窗口至少覆盖一个发布周期；SW 预缓存清单同理。
  7. SW 不要无条件 skipWaiting：先让旧页面安全结束，或提示用户更新；导航请求走 Network First + 离线兜底。
  8. SW 缓存必须版本化并可清理：缓存名含构建版本，activate 删除旧版本；避免磁盘配额被历史版本撑爆。
  9. 压缩只对文本：Brotli/gzip 对 HTML/JS/CSS/JSON/SVG 有效，对 JPEG/PNG/WebP/WOFF2 无效甚至变大；图片优先换格式（AVIF/WebP）。
  10. 资源提示只调时机，不减肥：preload 只放当前页确定要用的资源，prefetch 只放高概率下一页资源，preconnect 控制在 3~4 个关键域。
  11. 字体子集化 + font-display: swap：中文按 unicode-range 切片，preload 带 crossorigin；不要为了"字体一致"让首屏文字长时间隐形。
  12. 用数据验证缓存效果：看 CDN 命中率、回源率、Age 分布与 304 比例；不要凭感觉调 TTL。
