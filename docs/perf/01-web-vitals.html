Web 性能指标与真实用户监控（Core Web Vitals） ​

面向前端开发人员的性能度量参考资料 —— 优化最怕"凭感觉"：实验室 100 分，线上用户依然觉得卡。本章讲清 Lab 与 Field 的差异、Core Web Vitals（LCP / INP / CLS）与辅助指标（FCP / TTFB / TBT）的准确定义与阈值，并落到一套可上线的 RUM 方案：PerformanceObserver、web-vitals、自定义 mark/measure、sendBeacon 上报、采样维度与分级告警。

1. 概念解释 ​

1.1 Lab 与 Field：两种测量环境 ​

维度Lab（实验室）Field（真实用户）
数据来源Lighthouse / WebPageTest / 本地 Performance 面板线上真实设备、网络、地域的匿名埋点
环境固定机型与带宽、冷启动、无缓存CPU、网络、后台进程、缓存状态千差万别
优点可复现、可归因、能看火焰图反映真实体验，可按人群切片
缺点与真实体验偏差大噪声大、只能看结果不易定位原因
典型指标TBT、Lighthouse Score、Speed IndexLCP、INP、CLS 的 p75
用途开发期定位、回归门禁上线验收、告警、体验考核

正确姿势是 Field 定问题、Lab 找原因：先用真实用户数据发现"哪个页面、哪类设备、哪个分位在退化"，再回 Lab 用可控环境复现并逐层拆解（网络、主线程、渲染）。

1.2 Core Web Vitals 三件套 ​

  1. LCP（Largest Contentful Paint，最大内容绘制）：视口内最大一块内容完成绘制的时间，衡量加载体验。统计 <img>、<image>、<video> 封面与块级文本；CSS 背景图不计入，只凭"视觉上最大"猜 LCP 是常见误判。
  2. INP（Interaction to Next Paint，交互到下一次绘制）：用户点击 / 轻触 / 按键后，到界面下一次可见变化的延迟，取整页交互的近似高百分位（排除极端离群）。2024 年 3 月起取代 FID——FID 只测首次交互的输入延迟，漏掉处理与渲染耗时。
  3. CLS（Cumulative Layout Shift，累积布局偏移）：意外布局偏移的累计分值，衡量视觉稳定性。单次偏移分 = 影响面积比例 × 位移距离比例；CLS 取"会话窗口"内最大累计值（相邻偏移间隔小于 1 秒归入同窗口，窗口最长 5 秒）。用户输入后 500ms 内的偏移不计入（hadRecentInput）。

1.3 辅助指标：FCP、TTFB、TBT ​

指标含义作用归属
FCP首次绘制出任意内容（文字、图片、非空白 SVG/Canvas）的时间白屏时长的直接度量Field + Lab
TTFB请求发出到收到第一个响应字节反映 DNS/TCP/TLS/服务端/CDN 健康度，是 LCP 的地基Field + Lab
TBT主线程被长任务（>50ms）阻塞的时间总和实验室里替代 INP 的主线程繁忙度指标仅 Lab

TBT 需要精确的长任务切片，真实用户端噪声大、开销高，因此不进 Field 报表。线上想近似看主线程压力可采集 longtask，但口径与 TBT 不同，不要混用。

1.4 阈值：good / needs improvement / poor ​

Field 数据以 p75 判定，官方阈值如下：

指标良好需改进差说明
LCP≤ 2.5s2.5s – 4s> 4s超过 4s 多数用户感到明显等待
INP≤ 200ms200ms – 500ms> 500ms200ms 内通常被认为"即时响应"
CLS≤ 0.10.1 – 0.25> 0.250.1 内视觉上基本无感
FCP≤ 1.8s1.8s – 3s> 3s首屏白屏的直接信号
TTFB≤ 800ms800ms – 1800ms> 1800ms服务端 / 网络链路体检

一个页面某项指标的 p75 落在"需改进"，意思是"有 25% 的访问体验已经受损"，而不是平均值差。CWV 通过要求三项都达到 good 的 p75。

1.5 为什么是 p75，而不是平均值 ​

  • 平均值被长尾稀释：100 次访问里 80 次 1s、20 次 8s，平均 2.4s 看似还行，但五分之一用户经历了灾难性等待。
  • p75 是多数人的底线：表示 75% 的访问优于该值，兼顾覆盖率与尾部风险。
  • 必须分组聚合：按页面模板、设备类型、网络类型、地域、版本分别取 p75；混在一起算会被访问量大的好页面掩盖问题。
  • 样本量要够：单分组每天至少几十到上百次采样才有统计意义；低流量页面可延长到 7 天滚动窗口或按模板聚合。

1.6 指标背后的"人感" ​

主线程被 300ms 长任务占住时，点击反馈与动画全部排队——这就是 INP 与 TBT 恶化的直接原因，渲染流水线机制见 动画与过渡 1.3 节。首屏资源误用懒加载、preload 滥用、图片无尺寸，分别会伤 LCP 与 CLS，细节见 HTML5 实用能力补充。业务计算（排序、解析大 JSON、加密）应挪到 Worker，见 Web Workers。持续观察布局偏移与 DOM 变化，PerformanceObserver 与 MutationObserver 是同一套"浏览器择时回调"思路，见 Observer 三件套。

2. 语法说明 ​

2.1 PerformanceObserver 的 entryType 速查 ​

js
const po = new PerformanceObserver((list) => {
  for (const entry of list.getEntries()) {
    console.log(entry.entryType, entry.startTime, entry.duration);
  }
});
po.observe({ type: 'largest-contentful-paint', buffered: true });
entryType关键字段用途备注
navigationresponseStart、loadEventEndTTFB 与各阶段耗时导航一次，也可用 getEntriesByType
paintname、startTimeFCP 采集只有 first-paint / first-contentful-paint
largest-contentful-paintstartTime、size、elementLCP 采集随新的大内容出现而更新，取最终值
layout-shiftvalue、hadRecentInputCLS 采集必须过滤 hadRecentInput
eventduration、interactionIdINP 采集需 durationThreshold，默认 104ms
first-inputduration、processingStart旧 FID / 首次输入参考已被 INP 取代
longtaskduration、attribution长任务定位、TBT 近似仅 > 50ms 产生
resourcename、duration、transferSize资源耗时与体积配合 initiatorType 看发起者
mark / measurestartTime、duration、detail业务自定义分段由 performance.mark/measure 产生
elementidentifier、renderTimeElement Timing元素需加 elementtiming 属性

三个必须知道的细节：

  1. buffered: true：SDK 在 load 之后才初始化时，仍能拿到此前产生的条目，否则会漏掉 FCP/LCP。
  2. 两种 observe 写法不能混用：{ entryTypes: [...] } 是多类型订阅，{ type, buffered } 是单类型 + 缓冲。
  3. 不支持的 entryType 不报错：浏览器通常静默忽略，务必用 PerformanceObserver.supportedEntryTypes 做能力检测。

2.2 web-vitals 库：五个一行式 API ​

js
import { onLCP, onINP, onCLS, onFCP, onTTFB } from 'web-vitals';

function report(metric) {
  // { name, value, rating, delta, id, navigationType, entries }
  console.log(metric.name, metric.value.toFixed(1), metric.rating);
}

onLCP(report); onINP(report); onCLS(report); onFCP(report); onTTFB(report);
onCLS(report, { reportAllChanges: true }); // 调试期可选
API指标默认上报时机备注
onLCPLCP页面隐藏 / 卸载取最终值而非首个候选
onINPINP页面隐藏 / 卸载整页交互的高百分位近似
onCLSCLS页面隐藏 / 卸载内部实现会话窗口与输入过滤
onFCPFCP首次绘制后通常最早可用
onTTFBTTFB导航响应后值为 responseStart

v4 起 onFID 已移除；确需历史 FID 时用 first-input 自行采集。库对不支持的 API 会安静跳过——"Safari 上 INP 为空"是预期行为，不是接入 bug。

2.3 自定义 mark / measure ​

js
performance.mark('route:start');
// ...路由切换与首屏渲染...
performance.mark('route:end');
performance.measure('route:render', 'route:start', 'route:end');

const m = performance.getEntriesByName('route:render').at(-1);
console.log(m.startTime, m.duration);

// 带业务维度（较新 Chrome 支持 detail）
performance.measure('api:list', {
  start: 'api:start', end: 'api:end',
  detail: { endpoint: '/api/list', cached: false },
});

performance.clearMarks('route:start');
performance.clearMeasures('route:render');

要点：startTime 相对 performance.timeOrigin，不要与 Date.now() 混算；measure 会出现在 DevTools Performance 面板的 Timings 轨道；打点名统一前缀（如 app:）并在上报端做白名单；若页面经过预渲染，所有时间需减去 activationStart 才是用户感知时间。

2.4 RUM 上报：sendBeacon 与 keepalive ​

页面隐藏 / 卸载时普通 fetch 会被中断，两种可靠做法：

js
const payload = {
  page: location.pathname,
  vitals: { lcp: 2100, inp: 180, cls: 0.04, fcp: 1200, ttfb: 420 },
  dims: { device: 'mobile', conn: '4g', release: '2026.10.1' },
  sid: 'anon-7f3a', ts: Date.now(),
};

// 1) sendBeacon：后台可靠发送，不阻塞卸载
navigator.sendBeacon('/rum',
  new Blob([JSON.stringify(payload)], { type: 'application/json' }));

// 2) fetch + keepalive：可带请求头、可读响应，但请求体限额更严
fetch('/rum', {
  method: 'POST', body: JSON.stringify(payload),
  headers: { 'Content-Type': 'application/json' },
  keepalive: true, credentials: 'same-origin',
});
方式优点限制适用
sendBeacon不阻塞卸载、跨页面生命周期可靠不能自定义请求头（Blob 可设类型）、载荷约 64KB纯 JSON 埋点
fetch keepalive可自定义头、能读响应、可复用请求封装请求体上限更严、并发有限制需鉴权头或失败处理

触发时机：CWV 最终值必须在页面"不再变化"时取。同时监听 visibilitychange（hidden）与 pagehide，用 flag 去重；不要只依赖 beforeunload（移动端经常不触发）。

2.5 采样与维度：别让监控自己拖慢页面 ​

  • 采样率：全量上报在百万 DAU 下会打爆存储；通常 5%–20% 足够看趋势，A/B 期可提到 50%–100%。采样要在会话入口随机决定一次，整条会话保持一致。
  • 维度：page（路由模板，不要带 ID）、device（mobile/desktop/tablet）、conn（navigator.connection.effectiveType，不可用留空）、navigationType、release。维度基数要小，完整 URL 带查询参数会让聚合失去意义。
  • 匿名与合规：会话 ID 用随机数，不拼用户标识；需要跨会话分析时存哈希后的稳定 ID，并纳入隐私政策。
  • 开销控制：PerformanceObserver 本身开销很低，但频繁序列化大对象、在 scroll/input 回调里同步上报会反噬 INP。统一"内存累积 → 页面隐藏时一次发送"。

2.6 性能预算与分级告警 ​

js
// 单一事实来源：CI 与线上监控共用
const THRESHOLDS = {
  LCP: { warn: 2500, error: 4000 },
  INP: { warn: 200, error: 500 },
  CLS: { warn: 0.1, error: 0.25 },
  FCP: { warn: 1800, error: 3000 },
  TTFB: { warn: 800, error: 1800 },
};
const LAB_BUDGET = { lcp: 2500, tbt: 300, cls: 0.1, firstScreenJsKB: 180 };

function grade(metric, p75) {
  const t = THRESHOLDS[metric];
  if (p75 > t.error) return 'error';
  if (p75 > t.warn) return 'warn';
  return 'good';
}

Lab 预算进 CI 卡门禁（Lighthouse 或自建采集），Field 阈值进监控做告警。告警以 1 小时 / 1 天窗口的 p75 为基线，连续两个窗口越线才升级，同时对比上一版本的回归幅度（如 LCP +300ms），避免缓慢劣化被绝对阈值掩盖；每条告警必须带 owner，否则会变成没人处理的噪声墙。

4. 使用场景示例 ​

4.1 最小可用的 Core Web Vitals 采集器 ​

场景描述：不引依赖，采集 FCP、TTFB、LCP 最终值与 CLS 会话窗口，页面隐藏时通过 sendBeacon 上报。

js
const nav = performance.getEntriesByType('navigation')[0] || {};
const data = {
  fcp: null, lcp: null, cls: 0, sent: false,
  ttfb: nav.responseStart ? Math.max(0, nav.responseStart) : null,
};

new PerformanceObserver((list) => {
  for (const e of list.getEntries()) {
    if (e.name === 'first-contentful-paint') data.fcp = e.startTime;
  }
}).observe({ type: 'paint', buffered: true });

new PerformanceObserver((list) => {
  data.lcp = list.getEntries().at(-1).startTime; // 每次候选都覆盖，取最终值
}).observe({ type: 'largest-contentful-paint', buffered: true });

let sessionValue = 0, sessionStart = 0, lastTs = 0, maxCls = 0;
new PerformanceObserver((list) => {
  for (const e of list.getEntries()) {
    if (e.hadRecentInput) continue;
    const t = e.startTime;
    if (t - lastTs > 1000 || t - sessionStart > 5000) { // 窗口重置：1s 间隔 / 5s 上限
      sessionStart = t; sessionValue = 0;
    }
    sessionValue += e.value; lastTs = t;
    maxCls = Math.max(maxCls, sessionValue); data.cls = maxCls;
  }
}).observe({ type: 'layout-shift', buffered: true });

function flush() {
  if (data.sent) return;
  data.sent = true;
  navigator.sendBeacon?.('/rum', new Blob(
    [JSON.stringify({ ...data, page: location.pathname, ts: Date.now() })],
    { type: 'application/json' }));
}
addEventListener('visibilitychange', () => {
  if (document.visibilityState === 'hidden') flush();
});
addEventListener('pagehide', flush);

逐段注释：buffered: true 保证脚本晚于首次绘制时仍能取到 FCP；LCP 的最后一个候选才是最终值；CLS 的窗口判定最容易漏，1s 间隔 + 最长 5s 缺一不可；flush 用 sent 去重，避免两个事件重复发送。

预期效果：控制台能看到随页面使用不断更新的对象，切后台 / 关标签时发出一次请求。

4.2 web-vitals + 业务维度 + 客户端评级 ​

场景描述：用官方库采集五项指标，附带设备、网络、页面模板与版本，客户端先算评级。

js
import { onLCP, onINP, onCLS, onFCP, onTTFB } from 'web-vitals';

const dims = {
  page: location.pathname.replace(/\/\d+$/, '/:id'), // 去高基数 ID
  device: matchMedia('(max-width: 768px)').matches ? 'mobile' : 'desktop',
  conn: navigator.connection?.effectiveType || '',
  release: window.__APP_VERSION__ || 'dev',
};
const queue = [];
const send = () => {
  if (!queue.length) return;
  navigator.sendBeacon('/rum', new Blob([JSON.stringify(queue.splice(0))],
    { type: 'application/json' }));
};
function collect(metric) {
  queue.push({
    name: metric.name, value: metric.value, rating: metric.rating,
    delta: metric.delta, id: metric.id,
    navigationType: metric.navigationType, dims,
  });
  send();
}
onFCP(collect); onTTFB(collect); onLCP(collect);
onINP(collect); onCLS(collect);
addEventListener('visibilitychange', () => {
  if (document.visibilityState === 'hidden') send();
});

逐段注释：page 模板化是维度治理的关键——直接上报 /order/123456 会让每个订单一个维度，p75 永远没样本；rating 由库按官方阈值计算，前端先标记可让服务端只做聚合；id 是访问级 ID，多次 delta 可拼成"本次访问的指标轨迹"。

预期效果：报表可按"页面模板 × 设备 × 网络 × 版本"四维下钻，且每组样本足够。

4.3 用 mark/measure 拆解首屏关键路径 ​

场景描述：PM 问"首屏慢是接口慢还是渲染慢"，用 User Timing 拆成"路由开始 → 数据就绪 → 首帧"。

js
performance.mark('app:route-start');
const dataPromise = fetch('/api/home').then((r) => r.json());
performance.mark('app:data-requested');
const data = await dataPromise;
performance.mark('app:data-ready');
performance.measure('app:api', 'app:data-requested', 'app:data-ready');

renderHome(data);
requestAnimationFrame(() => {
  performance.mark('app:first-frame');
  performance.measure('app:render', 'app:data-ready', 'app:first-frame');
  performance.measure('app:total', 'app:route-start', 'app:first-frame');
  const measures = performance.getEntriesByType('measure')
    .filter((m) => m.name.startsWith('app:'));
  navigator.sendBeacon('/rum', new Blob(
    [JSON.stringify(measures.map((m) => ({ name: m.name, duration: Math.round(m.duration) }))],
      { type: 'application/json' }));
});

逐段注释：用 requestAnimationFrame 而不是 setTimeout 标记首帧，因为 rAF 回调发生在下一帧绘制前；三段耗时相加应约等于总时长，差很多说明中间有等待（微任务、字体、图片解码）；上报只带名字与整数时长，控制载荷。

预期效果：报表直接看到"接口 800ms / 渲染 300ms / 路由等待 200ms"的拆分。

5. 实际应用案例分析 ​

案例一：电商详情页 INP 从 420ms 降到 160ms ​

背景：某电商 H5 详情页 INP p75 = 420ms（需改进），低端机达 610ms。

排查：按设备分组确认低端安卓是重灾区（桌面仅 130ms）；采集 event.duration + interactionId，发现"加入购物车"与"切换规格"贡献 70% 高延迟；Lab 用 CPU 6x 降速复现出 180ms 长任务——规格矩阵同步 JSON.parse 了 1.2MB SKU 数据并重算全部组合。结论：不是点击处理写慢了，而是点击触发了同步大计算。

措施效果
SKU 解析移到 Web Worker点击路径少 120ms
规格组合按需计算 + 缓存重复点击直接命中
列表改虚拟滚动首次渲染少 60ms
按钮态反馈提前到 pointerdown感知延迟下降

结果：INP p75 420ms → 160ms，低端机 610ms → 290ms，加购成功率提升约 3%（灰度对照）。

案例二：内容站 CLS 从 0.32 降到 0.04 ​

背景：资讯站改版后 CLS p75 = 0.32（差），用户投诉"读到一半页面跳走"。

归因：按"发生时间 + 偏移元素"聚合 layout-shift，三个来源：① 顶部广告位无尺寸，250px 横幅插入时单次偏移 0.18；② 列表封面图无宽高，加载后连续撑开容器；③ 标题字体 font-display: block 在 2.8s 才到达，文字可见时跳变。

措施效果
广告位 min-height + 骨架占位消除最大单次偏移
图片补 width/height + height:auto图片不再撑开布局
字体改 swap + preload文字立即可见
首屏外模块 content-visibility: auto减少不可见区域抖动

结果：CLS p75 0.32 → 0.04，LCP 顺带从 3.1s 降到 2.4s（字体不再阻塞首屏文本）。

案例三：平均值报表掩盖了真问题 ​

某团队长期看"全站平均 LCP = 2.1s"以为达标。改按设备 + 页面模板取 p75：桌面首页 1.8s（good），移动端商品详情 5.2s（poor），但只占 8% 流量被平均值掩盖；再按网络分组，4G 用户 p75 = 6.1s，原因是首屏主图 1.8MB 未压缩且无 preconnect。压缩 + 尺寸适配 + fetchpriority="high" 后降到 3.4s，接口串行改并行后降到 2.6s。聚合方式决定了你能看见什么问题。

6. 最佳实践与常见坑 ​

6.1 ✗ 与 ✓ 对比速查 ​

✗ 反例✓ 正例
数据口径全站混算平均值按页面模板 / 设备 / 网络分组取 p75
LCP 取值取第一个候选就上报取最后一个候选，隐藏时定稿
CLS 计算所有 layout-shift 的 value 直接相加过滤 hadRecentInput，按会话窗口取最大累计
INP 采集用 first-input 当作 INP用 event + interactionId，整页聚合
上报时机只在 beforeunload 发送visibilitychange + pagehide，sendBeacon / keepalive
不支持平台上报 0，报表显示"完美"上报 null 并标注指标不可用
打点命名start、end 这类通用名app:route-start 等命名空间前缀
采样100% 全量、每条指标立即发请求入口随机采样 + 内存累积 + 隐藏时批量发送

6.2 十二条落地守则 ​

  1. 先定义"什么算好"再优化：把 LCP 2.5s / INP 200ms / CLS 0.1 的 p75 目标写进验收标准。
  2. Field 定问题、Lab 找原因：不要用 Lighthouse 分数替代线上验收，也不要用 RUM 数据直接猜代码问题。
  3. 必须开 buffered: true：监控 SDK 常在加载后才初始化，不开缓冲会漏掉早期 FCP/LCP。
  4. LCP 只认最终值：新的大内容会替换旧候选，在 visibilitychange 时定稿，避免上报半成品。
  5. CLS 不是简单累加：会话窗口（1s 间隔 / 5s 上限）与 hadRecentInput 缺一不可，最好直接用 web-vitals。
  6. INP 要看整页交互：只测首次点击会漏掉列表操作、表单提交；保留 interactionId 与目标元素便于定位。
  7. 不要用 Date.now() 算性能时间：performance.now() / entry.startTime 是高精度单调时钟，混用会产生负值或漂移。
  8. 上报要去重与限流：同一指标可能多次回调，按 metric.id + name 去重，批量发送。
  9. 维度设计要克制：页面模板化、设备三档、网络四档、版本号足够了；高基数维度会让 p75 失去样本。
  10. 采样率与目标匹配：趋势观察 5%–20% 足够，A/B 实验期可提高；采样必须在会话入口固定。
  11. 预算与告警同源：CI 的 Lab 预算与线上 Field 阈值放同一配置文件，避免两套标准互相打架。
  12. 告警带 owner 与回归幅度：只看绝对阈值会漏掉从 1.2s 慢慢爬到 2.4s 的劣化；连续窗口 + 版本对比才可靠。
