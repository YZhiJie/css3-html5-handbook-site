性能审计与线上监控：从 Lab 到 Field 的闭环 ​

面向前端开发人员的性能优化参考资料 —— 性能优化最怕"改完感觉快了"。本章建立一条可验证的闭环：实验室（Lab）用 Lighthouse/DevTools 定位问题，现场（Field）用 RUM 用 p75 验证收益，性能预算与 CI 门禁防止回退，线上告警与排查决策树兜住事故。同时讲清 TBT 与 INP 的关系、sendBeacon 上报、source map 归因、灰度/AB 验证这些工程细节。

1. 概念解释 ​

1.1 Lab 与 Field：两种真相 ​

维度Lab（实验室）Field（现场）
数据来源Lighthouse、DevTools、自建基准脚本真实用户埋点（RUM）、CrUX
环境固定机型 + 固定限速 + 清空缓存真实设备、网络、缓存状态、并发
优势可复现、可归因、可阻断 CI反映真实分布，能验证收益
局限无法代表长尾设备与真实交互噪声大、需要样本量与维度拆分
核心指标LCP/TBT/CLS 的单次值p75 的 LCP/INP/CLS

结论：Lab 用来"找原因"，Field 用来"证效果"。只盯 Lighthouse 分数会出现"实验室 100 分、线上依旧卡"的错觉；只盯 RUM 又无法定位到具体代码。两者必须成对使用。

1.2 Lighthouse 审计流程与评分 ​

Lighthouse 的一次运行大致是：采集（启动浏览器、注入探针、限速）→ 计算指标 → 跑审计规则 → 按权重汇总。Performance 分类的权重（Lighthouse 10+）：

指标权重说明
LCP（最大内容绘制）25%首屏主内容出现时间
TBT（总阻塞时间）30%FCP 到结束期间超过 50ms 的任务阻塞时间总和
CLS（累积布局偏移）25%布局不稳定程度
FCP（首次内容绘制）10%首次出现文字/图片
Speed Index10%视觉填充速度

每个指标先由原始值映射为 0~100 的分项得分（对数正态曲线），再按权重加权。分数不是线性换算：LCP 从 4.0s 降到 3.0s 的分数提升，可能远大于 1.0s 降到 0.5s。Lighthouse 默认模拟"移动端 + 慢速 4G + 4 倍 CPU 降速"，单次结果方差可达 ±10 分；CI 里应跑 3~5 次取中位数，并固定版本与配置。

1.3 DevTools Performance：火焰图、网络瀑布、CPU 剖面 ​

  • 火焰图（Flame Chart）：横轴时间、纵轴调用栈。宽条代表耗时长；主线程上的**长任务（>50ms）**会表现为一整块"红/黄"宽条，期间无法响应输入。
  • 网络瀑布（Network）：看资源串行/并行、优先级、TTFB、下载耗时。瀑布呈"阶梯"往往意味着请求链依赖（JS 里再 fetch、CSS 里 @import）。
  • CPU 剖面（Bottom-Up / Call Tree）：按"自身耗时"聚合函数，定位热点；Self 高说明函数本身慢，Total 高但 Self 低说明它在等子调用。
  • Frames / Interactions：查看掉帧与交互延迟，配合长任务定位"点下去多久才有反应"。

1.4 TBT 与 INP：实验室代理 ≠ 线上体验 ​

指标类型含义阈值（p75）
TBTLabFCP 之后所有 >50ms 任务的 (时长 - 50ms) 之和良好 <200ms，差 >600ms
INPField一次访问中所有交互的延迟，取较差值（p75 聚合）良好 ≤200ms，差 >500ms

关系：TBT 衡量"主线程被长任务占住的总量"，INP 衡量"用户每次点击/输入的等待"。TBT 低通常意味着 INP 风险小，但不能划等号：一个页面加载时很干净（TBT 低），用户滚动到第 3 屏后触发一个 300ms 的筛选计算，INP 依然会很差。INP 已于 2024 年 3 月正式取代 FID 成为 Core Web Vitals 的响应性指标。优化思路见 主线程长任务。

1.5 RUM 看板：p75、维度、采样与上报 ​

RUM（Real User Monitoring）的核心不是"收集所有数据"，而是用可承受的采样回答分布问题：

  1. p75 而非平均值：平均值会被少数极快用户拉低；Core Web Vitals 的"良好"判定按第 75 百分位。
  2. 维度拆分：按路由、设备档位（低端 Android/iPhone）、网络类型（4G/5G/Wi-Fi）、地域、版本号拆分，否则长尾问题被平均掉。
  3. 采样：高流量站点按 1%~10% 采样，或"每个会话只报一次关键指标"；采样率要随版本对比需求调整，避免 AB 实验样本不足。
  4. 上报时机：页面卸载时用 navigator.sendBeacon()（不阻塞关闭、可跨页），或在 visibilitychange 进入 hidden 时上报；避免 unload（移动端常不触发）。
  5. 指标库：用 web-vitals 采集 LCP/CLS/INP/TTFB/FCP，web-vitals/attribution 还能给出 LCP 元素、INP 目标元素等归因信息。

1.6 性能预算、CI 门禁与回归告警 ​

性能预算是把"感觉"变成"数字"：

类型示例阈值说明
指标预算LCP ≤2.5s、INP ≤200ms、CLS ≤0.1（p75）对齐 Core Web Vitals 良好线
体积预算首屏 JS ≤170KB（gzip）、CSS ≤50KB、首屏图片 ≤200KB经验值，按业务与用户网络调整
数量预算首屏请求 ≤30 个、第三方域 ≤5 个控制连接与瀑布
时间预算TTFB ≤800ms、TBT ≤200ms（Lab）服务端与主线程双约束

CI 门禁：Lighthouse CI 在每次 PR 上跑 lhci autorun，用 assert 断言分数/指标/体积；budget.json 由 Lighthouse 的 --budget-path 读取，超预算直接失败。体积侧可配合 size-limit 做 bundle 级别检查。

回归告警：发布后对比"当前版本 vs 上一版本"的 p75，按路由与设备维度看涨幅；设阈值（如 LCP p75 恶化 >20% 或 >500ms）触发告警，而不是只看绝对值。

1.7 source map 归因、灰度与 AB ​

  • source map：线上错误栈与慢函数要映射回源码，必须保留 source map；但不要公开托管（会泄露源码）。用 hidden-source-map 构建并在 CI 上传到监控平台（Sentry 等），按版本号关联。
  • 灰度/AB：新优化先放 1%~5% 流量，对比 p75 与业务指标（转化、留存），样本量与观察窗口足够后再全量；异常时按版本/开关快速回滚。

2.3 RUM 采集与 sendBeacon 上报 ​

js
// 用 web-vitals 采集，页面隐藏时批量上报
import { onLCP, onCLS, onINP, onTTFB } from 'web-vitals';

const queue = [];
const report = (metric) => {
  queue.push({
    name: metric.name,
    value: metric.value,
    rating: metric.rating,
    id: metric.id,
    route: location.pathname,
    device: matchMedia('(max-width: 768px)').matches ? 'mobile' : 'desktop',
    version: __APP_VERSION__            // 构建注入，用于回归对比
  });
};

onLCP(report);
onCLS(report);
onINP(report);
onTTFB(report);

function flush() {
  if (!queue.length) return;
  const payload = new Blob([JSON.stringify(queue)], { type: 'application/json' });
  if (navigator.sendBeacon) {
    navigator.sendBeacon('/rum', payload);   // 规范建议单次 ≤64KiB
  } else {
    fetch('/rum', { method: 'POST', body: payload, keepalive: true });
  }
  queue.length = 0;
}

addEventListener('visibilitychange', () => {
  if (document.visibilityState === 'hidden') flush();
});

4. 使用场景示例 ​

4.1 场景一：用检查清单把审计变成可执行动作 ​

Lighthouse 的"诊断"项很多，但团队真正需要的是一张可勾选、可算分、可对齐预算的清单。示例页把审计拆成 10 项：LCP 图优化、字体 preload、TBT、CLS、图片格式、压缩、缓存头、第三方数量、DOM 规模、INP 埋点。每项带权重与"是否通过"，实时算加权分并判断是否达到 90 分门禁。

js
// 权重与得分：0 未做 / 0.5 部分 / 1 完成
const audits = [
  { id: 'lcp', weight: 25, done: false },
  { id: 'tbt', weight: 20, done: false },
  { id: 'cls', weight: 15, done: false },
  // ...
];
const score = audits.reduce((sum, a) => sum + a.weight * a.done, 0)
            / audits.reduce((sum, a) => sum + a.weight, 0) * 100;

关键点：清单不是替代 Lighthouse，而是把"审计结论"翻译成"工程任务"；每项都应绑定负责人与验收标准，否则分数只是自嗨。

4.2 场景二：火焰图阅读与长任务归因 ​

示例页用内联 SVG 绘制主线程时间轴，每个矩形是一个任务；超过 50ms 的标红。点击红块显示：任务时长、阻塞时间（duration - 50）、疑似原因（大循环/JSON 解析/布局抖动）与建议动作。

js
// 阻塞时间 = 所有 >50ms 任务超出 50ms 的部分之和
const blocking = tasks
  .filter((t) => t.duration > 50)
  .reduce((sum, t) => sum + (t.duration - 50), 0);

预期效果：一眼看出"总阻塞时间"来自哪几个宽条；点击宽条能看到它落在 FCP 前还是后——FCP 前主要影响 FCP/LCP，FCP 后主要影响 TBT/INP。更系统的长任务治理见 主线程长任务。

4.3 场景三：性能预算计算器 ​

输入首屏 JS/CSS/图片/字体体积（KB），与预算（170/50/300/100）对比，逐项给出"通过/超预算"和超出百分比；同时给出"压缩后估算"（文本按 gzip 约 30%、Brotli 约 25%，仅作教学估算）。

js
const budgets = { js: 170, css: 50, image: 300, font: 100 };
const actual = { js: 210, css: 48, image: 420, font: 90 };
const over = Object.keys(budgets).filter((k) => actual[k] > budgets[k]);

关键点：预算要写进 CI 才有约束力；本地计算器只用于方案评审时快速判断"这个需求会不会把首屏撑爆"。

4.4 场景四：线上故障排查决策树 ​

把"白屏/卡顿/慢加载"三条路径固化成决策树，值班同学按节点排查，避免凭直觉重启：

症状第一分支第二分支常见根因
白屏所有用户还是个别？全部 → CDN/发布；个别 → 本地缓存/SW发布缺产物、HTML 解析失败、chunk 404、SW 旧缓存
卡顿持续还是操作时？持续 → 内存/定时器；操作 → 长任务内存泄漏、无限循环、同步大计算、布局抖动
慢加载TTFB 还是下载/渲染慢？TTFB → 服务端/CDN；下载 → 体积/网络回源慢、未压缩、图片过大、请求瀑布

示例页把三条路径做成可点击的节点树，每个节点给出下一步动作与止损手段（回滚、purge、降级、关闭实验开关）。

5. 实际应用案例分析 ​

5.1 某电商：Lighthouse 96 分，线上 LCP 仍 4.2s ​

背景：大促主会场 Lighthouse 性能 96，但 RUM 显示低端 Android 的 LCP p75 4.2s。

排查：

  1. Lab 环境掩盖了设备差异：Lighthouse 模拟 4 倍降速，但真实低端机是 6~8 倍 CPU 与更慢的存储；在低端真机复测 LCP 直接翻倍。
  2. LCP 图按屏幕宽度下发：移动端拿到的仍是 2400px 大图，sizes 缺失导致 srcset 选错。
  3. 首屏 JS 里同步解析 300KB JSON：LCP 图下载完成后，主线程仍在解析，绘制被推迟。
  4. 第三方比价组件：在主线程同步注入，抢占带宽并触发额外布局。

措施：补 sizes/AVIF、JSON 解析移入 Worker、比价组件延迟到 requestIdleCallback、低端机灰度验证。结果：低端机 LCP p75 4.2s → 2.4s，Lighthouse 分数基本不变。结论：Lab 分数是下限保障，Field p75 才是验收标准。

5.2 某 SaaS：Lighthouse CI 门禁挡住一次体积回退 ​

背景：团队引入 lhci autorun，PR 必须 performance ≥90 且 total-byte-weight ≤500KB。

过程：

  1. 某次 PR 引入完整图标库，首屏 JS +180KB（gzip）；
  2. CI 的 budget.json 触发 script 预算超限，assert 同时报 total-byte-weight 失败；
  3. 开发者改为按需引入 + 路由分包，PR 通过。

踩坑：

  1. 单次跑分波动导致偶发失败 → 改为 numberOfRuns: 3 取中位数；
  2. 预算定得太死（初始 120KB）导致大量历史页面无法通过 → 先按现状 +10% 设基线，再逐步收紧；
  3. 只卡分数不卡体积 → 分数受多指标影响，体积回退可能被其他指标掩盖，必须双约束。

5.3 某后台：一次白屏事故的 12 分钟排查 ​

时间线：

  1. 0 分钟：告警"白屏率突增"，RUM 显示仅某个版本、某条路由；
  2. 2 分钟：确认 CDN 5xx 正常、HTML 200；排除全站故障；
  3. 5 分钟：该路由的 chunk 返回 404 → 发布时清理了旧产物，而部分用户仍持有旧 HTML；
  4. 8 分钟：回滚发布并恢复旧产物，白屏率回落；
  5. 12 分钟：确认根因是"HTML 缓存 + 旧 chunk 清理"的交叉窗口。

修复：HTML 改 no-cache、产物保留两个版本、chunk 加载失败提示刷新、SW 预缓存清单保留旧版本。沉淀：把决策树写进值班手册，并给白屏率单独设告警阈值。缓存侧细节见 资源缓存与分发优化。

6. 最佳实践与常见坑 ​

6.1 十条必须遵守的规则 ​

  1. Lab 找原因，Field 证效果：不要用一次 Lighthouse 分数宣布优化成功；用同版本、同维度的 p75 对比。
  2. 关注 p75，不看平均值：平均值会掩盖长尾；Core Web Vitals 的判定线本身就是 75 百分位。
  3. Lighthouse 必须固定配置：固定版本、设备预设、限速方式与运行次数；CI 里至少 3 次取中位数。
  4. TBT 不能替代 INP：加载期 TBT 好不代表交互快；把交互路径单独做长任务治理与 INP 埋点。
  5. RUM 必须带维度：路由、设备档位、网络、地域、版本五类维度至少保留三个，否则无法定位长尾。
  6. 上报用 sendBeacon + visibilitychange：不要依赖 unload；单次载荷控制在 64KiB 内，失败要有本地队列兜底。
  7. 预算写进 CI，不写在文档里：lhci autorun + budget.json + 体积检查，PR 不达标就阻断。
  8. 发布后做版本回归对比：按路由/设备对比上一版本 p75，设恶化阈值告警；只看绝对值会漏掉"慢慢变差"。
  9. source map 私有上传：hidden-source-map + CI 上传监控平台；公开 map 等于公开源码。
  10. 线上事故先止损再定位：回滚/关开关/purge 优先，保留现场（日志、版本、采样）后再分析。
  11. 灰度验证要有样本量与窗口：1%~5% 流量、至少 24 小时、覆盖完整业务周期，避免把波动当成收益。
  12. 指标归因到具体元素与代码：用 web-vitals/attribution 或火焰图定位 LCP 元素、INP 目标与热点函数，避免"知道慢但不知道慢在哪"。
