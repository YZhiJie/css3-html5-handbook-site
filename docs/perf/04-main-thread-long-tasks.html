主线程、长任务与任务切片 ​

面向前端开发人员的性能优化参考 —— 页面卡顿的本质，几乎都能归结为一句话：主线程在应该画出下一帧的时候，还在忙着别的事。JS 是单线程的，事件循环一次只能跑一个任务；超过 50ms 的任务被称为"长任务"，它会让点击延迟、输入卡顿、动画掉帧，并直接拉高 INP。本章从事件循环与 16.7ms 帧预算讲起，讲清长任务的判定、INP 的三段构成、布局抖动与 GC 停顿，再给出任务切片、Worker、虚拟列表、content-visibility 等一整套"把主线程还回去"的手段。

1. 概念解释 ​

1.1 事件循环：task → microtask → 渲染机会 ​

简化后的浏览器事件循环：

text
取一个 task（宏任务） → 执行到完成 → 清空 microtask 队列 → 是否到渲染时机？
  ├── 是 → Style → Layout → Paint → Composite（可能合并/跳过）
  └── 否 → 取下一个 task
  • task（宏任务）：一次脚本执行、一个 setTimeout 回调、一次事件回调、一次 postMessage 消息处理。一个 task 会整体执行完，中途不会被打断——这正是长任务会卡住页面的原因。
  • microtask（微任务）：Promise.then、queueMicrotask、MutationObserver 回调。每个 task 结束后会清空整个微任务队列，然后才可能渲染。用微任务做"切片"是无效的：微任务之间不会让出渲染与输入事件。
  • 渲染机会（rendering opportunity）：浏览器按屏幕刷新节奏（60Hz 约 16.7ms 一次，120Hz 约 8.3ms）尝试出帧；若主线程忙，帧就被跳过，表现为掉帧。

1.2 16.7ms 帧预算 ​

text
60Hz：1 帧 = 1000 / 60 ≈ 16.67ms
120Hz：1 帧 = 1000 / 120 ≈ 8.33ms

这 16.7ms 不是"全部给 JS"：一帧里还要做样式计算、布局、绘制、合成，以及浏览器自身的调度开销。业内常用的经验法则是单个 JS 任务控制在 5ms 以内，给渲染留出余量。超过 16.7ms 的任务至少丢一帧；超过 50ms 的任务会被 PerformanceObserver 记为 long task。

1.3 长任务（long task）：> 50ms ​

  • 定义来自 Long Tasks API：持续超过 50ms 的任务。50ms 约等于 3 帧，足以让一次点击的反馈明显延迟。
  • 长任务期间：输入事件排队、requestAnimationFrame 不执行、动画停在原地、滚动可能由合成器维持但内容不更新。
  • 常见来源：大循环/大数组处理、复杂 JSON 解析、同步布局抖动、大规模 DOM 插入、第三方脚本初始化、GC 停顿。
  • 测量：PerformanceObserver 监听 longtask，条目有 startTime、duration、attribution（部分浏览器提供来源）。Chrome/Edge 支持，Firefox/Safari 目前不支持，需要自建埋点。

1.4 INP 的三段构成 ​

INP（Interaction to Next Paint）衡量"一次交互到下一次画面更新"的耗时，2024 年 3 月起成为 Core Web Vitals 的稳定性指标。它把一次交互拆成三段：

阶段英文含义常见原因
输入延迟input delay从用户操作发生，到事件回调开始执行主线程正在跑长任务、微任务队列过长
处理时间processing time事件回调（含冒泡链上的所有监听器）执行的总时间回调里做重计算、同步读写布局、复杂状态更新
呈现延迟presentation delay回调结束到下一帧真正画到屏幕上样式/布局/绘制工作量大、帧被跳过、合成排队

三段相加就是这次交互的 INP。判定基线：≤ 200ms 良好，200~500ms 需改进，> 500ms 差。优化时要先分清是哪一段拖后腿：input delay 大 → 拆长任务；processing 大 → 精简回调/挪 Worker；presentation delay 大 → 减少渲染工作量（参见 GPU 合成与合成层）。指标定义与采集见 Web Vitals 与性能指标。

1.5 主线程阻塞的连锁反应 ​

主线程被占住时，受影响的远不止"点击没反应"：

  1. 输入延迟：pointerdown/click/keydown 排队，用户感知为"卡死"；
  2. 动画停摆：依赖主线程的动画（改 left、改 width、JS 逐帧）直接冻结；纯合成器动画仍可继续；
  3. 渲染滞后：样式/布局/绘制排队，滚动内容可能"追不上"手指；
  4. 超时与节流：setTimeout 回调被推迟，节流/防抖的时序失真；
  5. 连锁长任务：一个长任务结束后，积压的回调集中执行，可能形成新的长任务（"任务风暴"）。

1.6 布局抖动与 GC 停顿 ​

布局抖动（layout thrashing）：在同一个任务里交替"读布局 → 写样式"。

js
for (const el of items) {
  el.style.width = el.offsetWidth + 10 + 'px'; // 读→写→读→写……
}

每次读 offsetWidth / getBoundingClientRect() / scrollTop 时，如果之前有未应用的样式写入，浏览器必须同步完成一次布局才能返回准确值。循环 N 次就可能触发 N 次布局，成本呈线性放大。解法是读写分离：先批量读、再批量写；或把读放在 requestAnimationFrame、写放在下一个微任务/帧。

GC 停顿：V8 的垃圾回收大部分是增量/并发进行的，但主垃圾回收（major GC）仍可能造成短暂停顿。高频创建大对象（大数组、字符串拼接、闭包、DOM 节点）会增加 GC 压力。对策：复用对象/数组、避免在热循环里分配、减少一次性巨型数据结构、把大计算挪到 Worker（见 Web Workers）。

2. 语法说明 ​

2.1 任务切片原语对比 ​

原语让出后的调度时机是否给渲染机会典型用途注意
scheduler.yield()回到任务队列，优先级较高，通常很快恢复是（浏览器可插入渲染）首选切片原语（Chrome 129+）需特性检测；返回 Promise
scheduler.postTask()可指定 user-blocking/ user-visible/ background 优先级是需要优先级调度的任务Chrome 94+；可配 delay/signal
MessageChannel宏任务，无 setTimeout 的最小延迟钳制是兼容性最好的切片回退每次让出产生一条消息
setTimeout(fn, 0)宏任务，嵌套 5 层后最小约 4ms是兼容性兜底延迟不稳定，后台标签页被节流
requestAnimationFrame下一帧绘制前是（本身就是帧）逐帧更新 UI、进度条频率受刷新率限制；后台暂停
requestIdleCallback浏览器空闲时是非紧急的清理/预计算可能长时间不执行；有 50ms deadline；后台被节流
queueMicrotask / Promise.then当前 task 结束后立即否（微任务清空前不渲染）状态一致性、异步化不能用于切片，会饿死渲染

2.2 可中断任务模板（优先 scheduler.yield） ​

js
const hasSchedulerYield =
  typeof scheduler !== 'undefined' && typeof scheduler.yield === 'function';

const channel = new MessageChannel();
const waiting = [];
channel.port1.onmessage = () => {
  const resolve = waiting.shift();
  if (resolve) resolve();
};

function yieldToMain() {
  if (hasSchedulerYield) return scheduler.yield();       // 首选
  return new Promise((resolve) => {                       // 回退：宏任务
    waiting.push(resolve);
    channel.port2.postMessage(0);
  });
}

const nextFrame = () =>
  new Promise((resolve) => requestAnimationFrame(() => resolve()));

async function runInterruptible(totalMs, onProgress, isAborted) {
  let done = 0;
  let slices = 0;
  while (done < totalMs) {
    if (isAborted()) return false;                        // 每个切片检查中断
    const sliceStart = performance.now();
    // 真正的工作：按时间片跑，而不是按固定条数
    while (performance.now() - sliceStart < 4) {
      doHeavyWork();
    }
    done += performance.now() - sliceStart;
    onProgress(done / totalMs);
    await yieldToMain();                                  // 让出主线程
    if (++slices % 8 === 0) await nextFrame();            // 定期确保画面更新
  }
  return true;
}

要点：

  • 按时间切片而不是按固定条数，因为不同设备吞吐差异巨大；
  • 每个切片检查中断标志，让"停止"按钮真正生效；
  • 定期 await nextFrame() 保证进度条真的画出来，而不是只更新了 DOM 数据；
  • 避免切片过细（< 1ms 会让调度开销占比过高），也避免过粗（> 10ms 就接近帧预算上限）。

2.3 读写分离（消除布局抖动） ​

js
// ✗ 读写交替：每次读都强制同步布局
for (const el of items) {
  el.style.height = el.offsetHeight + 4 + 'px';
}

// ✓ 批量读 → 批量写
const heights = items.map((el) => el.offsetHeight);       // 只读一次
for (let i = 0; i < items.length; i++) {
  items[i].style.height = heights[i] + 4 + 'px';          // 之后只写
}

更彻底的做法是把读和写分到不同帧：requestAnimationFrame 里读、下一个任务里写；或使用 ResizeObserver / IntersectionObserver 这类"浏览器择时回调"（见 Observer 三件套），让浏览器自己挑时间通知你。

2.4 把计算挪进 Worker ​

js
// 主线程只负责收发消息，CPU 密集任务全部进 Worker
const worker = new Worker(URL.createObjectURL(new Blob([`
  self.onmessage = (e) => {
    const result = heavyCompute(e.data);   // 大循环/解析/排序
    self.postMessage(result);
  };
`], { type: 'text/javascript' })));

worker.postMessage(payload);                // 主线程立即返回
worker.onmessage = (e) => render(e.data);   // 结果回来再更新 UI

细节（结构化克隆、Transferable、超时与回收）见 Web Workers。原则：只有 CPU 密集任务才值得开线程；fetch、setTimeout 本身不阻塞主线程。

2.5 虚拟列表与 content-visibility ​

js
// 虚拟列表核心：只渲染视口窗口 + overscan
const ROW = 32, VIEW_H = 360;
const start = Math.floor(scrollTop / ROW) - 2;
const end = Math.min(total, start + Math.ceil(VIEW_H / ROW) + 4);
// 用占位高度撑开滚动条，用 translateY 定位渲染窗口
spacer.style.height = total * ROW + 'px';
windowEl.style.transform = `translateY(${start * ROW}px)`;
css
/* content-visibility：屏幕外子树跳过布局/绘制，但 DOM 仍在 */
.section {
  content-visibility: auto;
  contain-intrinsic-size: auto 600px;
}

区别：虚拟列表省的是 DOM 节点数量与内存；content-visibility 省的是离屏渲染成本。两者可以叠加使用。

2.6 防抖、节流与输入响应 ​

js
// 搜索输入：防抖，等用户停下来再发请求
input.addEventListener('input', debounce((e) => search(e.target.value), 250));

// 滚动/尺寸：节流，用 rAF 对齐到帧
window.addEventListener('scroll', () => {
  if (ticking) return;
  ticking = true;
  requestAnimationFrame(() => {
    update();
    ticking = false;
  });
}, { passive: true });
  • 防抖适合"只关心最终值"的场景（搜索、校验、自动保存）；
  • 节流/rAF 适合"持续变化但要限量"的场景（滚动、拖拽、resize）；
  • 输入框本身要保持"打字跟手"：输入值绑定不要做重计算，重活延后到防抖回调或 Worker；
  • 触摸/滚轮监听加 { passive: true }，避免浏览器等待监听器返回导致滚动延迟。

2.7 测量 API：longtask 与 Event Timing ​

js
// 长任务日志（Chrome/Edge）
if (PerformanceObserver.supportedEntryTypes?.includes('longtask')) {
  new PerformanceObserver((list) => {
    for (const entry of list.getEntries()) {
      console.log('长任务', entry.startTime.toFixed(0), entry.duration.toFixed(0) + 'ms');
    }
  }).observe({ type: 'longtask', buffered: true });
}

// 交互三段（Event Timing，Chrome/Edge）
new PerformanceObserver((list) => {
  for (const e of list.getEntries()) {
    const inputDelay = e.processingStart - e.startTime;          // 输入延迟
    const processing = e.processingEnd - e.processingStart;      // 处理时间
    const presentation = e.duration - (e.processingEnd - e.startTime); // 呈现延迟
    console.log(e.name, { inputDelay, processing, presentation });
  }
}).observe({ type: 'event', durationThreshold: 16, buffered: true });

durationThreshold 最小为 16ms；超过阈值的交互事件才会进入回调。注意 event 类型条目只覆盖部分事件，INP 的完整计算规则见 web.dev 的 INP 文档。

4. 使用场景示例 ​

4.1 场景一：大数据处理的进度条（可中断切片） ​

场景描述：导入 20 万行数据做统计，需要 1.2 秒计算；要求进度条平滑、可取消、期间页面可点击。

js
async function importData(rows, onProgress, signal) {
  let processed = 0;
  const chunk = 2000;
  const t0 = performance.now();

  while (processed < rows.length) {
    if (signal.aborted) throw new DOMException('已取消', 'AbortError');
    const sliceStart = performance.now();

    // 每个切片最多做 4ms，保证留出渲染时间
    while (processed < rows.length && performance.now() - sliceStart < 4) {
      const end = Math.min(rows.length, processed + chunk);
      for (; processed < end; processed++) {
        aggregate(rows[processed]);          // 纯计算
      }
    }

    onProgress(processed / rows.length);
    await yieldToMain();                     // 让出，进度条才能画出来
  }
  return performance.now() - t0;
}

const controller = new AbortController();
stopBtn.onclick = () => controller.abort();

预期效果：进度条每帧前进一小段，取消按钮随时生效；期间点击计数、输入框、滚动都不卡。

4.2 场景二：表格批量更新（读写分离） ​

场景描述：150 行表格，根据新数据批量调整行高与高亮。第一版在循环里"读一行、写一行"，每次点击卡 80~150ms。

js
function applyRows(rows) {
  // ① 批量读：一次性把需要的信息读出来
  const rects = rows.map((tr) => tr.getBoundingClientRect());

  // ② 批量写：之后不再回读布局
  rows.forEach((tr, i) => {
    tr.style.height = (rects[i].height + 2) + 'px';
    tr.classList.toggle('is-active', i % 3 === 0);
  });
}

预期效果：从 N 次同步布局降为 1 次；点击后的卡顿消失。可配合 示例 的读写分离实验观察耗时差异。

4.3 场景三：搜索框的输入响应 ​

场景描述：用户输入关键词，实时过滤 5000 条本地数据并渲染结果。

js
const filter = debounce((keyword) => {
  const result = data.filter((item) => item.name.includes(keyword));
  renderList(result);                    // 渲染交给虚拟列表
}, 200);

input.addEventListener('input', (e) => {
  updateInputEcho(e.target.value);       // 输入框回显：立即、极轻
  filter(e.target.value);                // 重活：延后
});

预期效果：打字时输入框零延迟（只更新一个文本节点），过滤在用户停顿 200ms 后执行；5000 条结果只渲染可视区。

5. 实际应用案例分析 ​

5.1 案例一：报表导出按钮引发的"页面假死" ​

背景：某 BI 中后台点击"导出明细"后，需要在前端拼装 30 万行 CSV。第一版用同步循环，整个页面冻结 5~8 秒，用户连续点击导致任务叠加，最终内存暴涨。

定位：longtask 日志显示单条任务 5.2s；event 条目显示 input delay 达到 4.8s；Performance 面板看到一整条超长 JS 块。

方案：

  1. 把 CSV 拼装挪进 Web Worker（见 Web Workers）；
  2. Worker 按 5 万行分片回传，主线程按 type: 'progress' 更新进度条；
  3. 导出按钮在任务期间禁用，避免任务叠加；取消用 AbortController + worker.terminate()。

结果：主线程零长任务，进度条平滑，取消即时生效；导出期间页面仍可正常操作。

5.2 案例二：商品筛选页的输入延迟 ​

背景：某电商筛选页，每次勾选筛选项都同步重算 1 万条商品并重建 DOM，用户快速勾选时输入延迟高达 300~500ms。

定位：event 条目显示 processing time 只有 30ms，但 input delay 有 400ms——说明每次勾选都排队等前一次的长任务。

方案：

  1. 筛选结果计算防抖 150ms，且只计算最新一次选择（丢弃中间状态）；
  2. DOM 渲染改为虚拟列表，只渲染可视区 20 条；
  3. 计算与排序挪进 Worker，勾选框的视觉反馈立即更新，不等结果。

结果：input delay 从 400ms+ 降到 20ms 以内，勾选"跟手"；INP 从"差"回到"良好"区间。

5.3 案例三：信息流首屏的 GC 与渲染压力 ​

背景：某内容信息流首屏一次性渲染 80 个卡片，每个卡片含多张图片与内联 SVG，首屏脚本 300ms，滚动时周期性卡顿。

定位：Performance 面板发现多次 major GC（约 20~40ms），以及大量 Paint；longtask 条目集中在首屏渲染阶段。

方案：

  1. 首屏只渲染 12 个卡片，其余交给 content-visibility: auto / 分页加载；
  2. 图片统一固定宽高比 + loading="lazy" + decoding="async"；
  3. 卡片模板复用，避免每次创建大量临时对象；
  4. 滚动监听改为 rAF 节流 + { passive: true }；
  5. 列表项不再逐个 will-change（参见 GPU 合成与合成层）。

结果：首屏 JS 任务从 300ms 降到 80ms 以内，滚动时的周期性长任务消失。

6. 最佳实践与常见坑 ​

  1. 先量后切：用 Performance 面板与 longtask 日志确认长任务真实存在与位置，再决定切分粒度；不要盲目把代码拆成无数 setTimeout。
  2. 单任务控制在 5ms 左右：给 16.7ms 帧预算留出样式、布局、绘制的余量；超过 50ms 必须拆。
  3. 切片用宏任务，不用微任务：Promise.then / queueMicrotask 不清空不渲染，用它"切片"只会让画面更晚出现。
  4. 优先 scheduler.yield：Chrome 129+ 提供更合理的恢复优先级；按 scheduler.yield → MessageChannel → setTimeout 降级。
  5. 切片必须可中断：每个切片检查 AbortSignal 或标志位；"停止"按钮要在下一片（通常几毫秒内）生效。
  6. 定期 requestAnimationFrame 保证绘制：只更新 DOM 数据不一定出帧，进度条要真的画出来。
  7. 避免读写交替：批量读、批量写；getBoundingClientRect / offsetWidth 不要在循环里和写样式混用。
  8. 把 CPU 密集任务交给 Worker：大循环、解析、排序、像素处理；主线程只做 UI 与消息收发（见 Web Workers）。
  9. 长列表用虚拟列表：1000 行只渲染可视区；content-visibility 解决离屏渲染，二者不冲突。
  10. 输入路径保持"极轻"：输入框回显立即执行，重计算防抖 150~300ms 或进 Worker；事件监听尽量 { passive: true }。
  11. 警惕 GC 停顿：复用数组/对象、避免热循环分配、拆分巨型数据结构；不要依赖手动 GC。
  12. requestIdleCallback 只做非关键任务：它有 timeout 兜底但仍可能长期不执行；首屏关键路径禁止依赖。
  13. 避免任务叠加：按钮点击后禁用/置 loading，长任务运行中拒绝重复触发；用 AbortController 取消旧任务。
  14. 在低端机与降速环境下验证：DevTools CPU 4×/6× 节流 + 真机；桌面高配环境会掩盖长任务的真实影响。
