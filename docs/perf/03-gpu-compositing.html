GPU 合成与合成层：把动画交给合成器线程 ​

面向前端开发人员的性能优化参考 —— 浏览器把一帧拆成「样式 → 布局 → 绘制 → 合成」四步，前 3 步都在主线程，只有合成可以由合成器线程和 GPU 独立完成。transform / opacity 动画之所以顺滑，是因为它们被提前"抬升"为独立合成层，主线程再忙也能继续播放。但合成层不是免费的：每一层都是一张占显存的纹理，层是预算，不是加速开关。本章讲清层的来源、内存账本、升级触发条件与回收时机，并用 DevTools 把"看不见的显存"量出来。

1. 概念解释 ​

1.1 一帧的四个阶段：Style → Layout → Paint → Composite ​

浏览器每画一帧，逻辑上要走过四步（这是简化模型，现代内核还有预绘制、栅格化、光栅分块等细节）：

阶段做什么典型触发属性成本量级
Style（样式计算）把选择器匹配到元素，算出每个属性的最终值修改 class、display、伪类变化中；选择器越复杂、元素越多越贵
Layout（布局/回流）计算每个盒子的位置与尺寸width/height、top/left、margin、padding、字体变化高；可能波及整棵子树甚至整页
Paint（绘制）把元素的像素画进图层位图（含阴影、模糊、渐变）background、color、box-shadow、filter高；大面积、大模糊时尤其明显
Composite（合成）把多个层按层级/变换合成到屏幕transform、opacity、层顺序变化低；可由合成器线程与 GPU 独立完成

关键结论：能停在 Composite 的动画，才能在主线程卡顿时继续走。改 left 会一路击穿 Layout 与 Paint；改 transform 只更新合成层的变换矩阵。前置知识见 动画与过渡 的 1.3 节与 变换 Transform 的 1.3 节。

1.2 主线程 vs 合成器线程 ​

  • 主线程（main thread）：跑 JS、样式计算、布局、绘制、以及大部分 DOM API。它是单线程的，任何长任务都会把上述所有工作排队（见 主线程与长任务）。
  • 合成器线程（compositor thread）：维护层树、处理滚动与合成层变换，把结果交给 GPU 光栅化/上屏。它与主线程并行，因此即使主线程被 JS 卡住，纯 transform/opacity 的合成层动画仍能继续播放。
  • 例外：如果动画需要主线程重新计算样式、布局或绘制（例如改 width、改 box-shadow、或动画过程中触发新的层内容），合成器就必须等主线程。所谓"合成器动画"，前提是帧内容已经准备好，只剩矩阵/透明度变化。

这也解释了为什么 will-change、translateZ(0) 在某些场景看起来"变流畅"：不是 GPU 算得更快，而是把工作从主线程挪到了合成器线程。

1.3 合成层、纹理与分块 ​

  • 合成层（composited layer）：浏览器为需要独立变换/独立绘制的元素分配的一份"画布"。一个层通常对应一张 GPU 纹理（texture）。
  • 纹理（texture）：显存中的位图。尺寸以设备像素计，即 CSS 尺寸乘以设备像素比 DPR。层被放大时纹理会变模糊，因为它是先栅格化再缩放。
  • 分块（tile）：大层不会被当作一整张超大纹理，而是切成小块（Chromium 常见 256×256 或 512×512），按需栅格化、按需上传。滚动容器、超长页面因此可以只保留视口附近的块。分块降低了峰值显存，但层数 × 块数仍是一笔账。
  • 层树（layer tree）：合成器线程按层级、裁剪、变换组织这些层；重叠顺序、z-index、position: fixed 等都会影响层的划分。

1.4 为什么 transform / opacity 便宜 ​

  1. 不触发布局：transform 不改变文档流，盒子位置与尺寸不变，Layout 可以直接跳过。
  2. 不一定触发绘制：如果元素已被提升为独立层，动画期间只是改矩阵；纹理内容不变，无需重新 Paint。
  3. 可交给合成器：合成器线程独立更新层的变换/透明度，主线程不参与，因此不受 JS 长任务影响。
  4. GPU 擅长矩阵与混合：平移/缩放/旋转是顶点变换，透明度是 alpha 混合，都是 GPU 的强项。

反例：opacity 动画若元素没有被提升，浏览器通常也会为其创建层以获得合成器动画；但 filter、box-shadow、background 等属性的动画仍可能逐帧重绘，具体取决于实现与元素是否已成层。

1.6 GPU 加速不是免费的：层是预算 ​

层的代价至少有四笔：

  1. 显存：每层一张纹理，层数 × 尺寸 × DPR² 直接吃 GPU 内存；移动端 GPU 与主内存共享带宽，爆掉会触发系统回收甚至进程被杀。
  2. 初始化/栅格化：新层首次出现要分配纹理、栅格化内容，可能造成首帧卡顿（尤其是首次 hover 才提升的元素）。
  3. 合成开销：层越多，合成器要排序、裁剪、混合的层就越多；大量重叠层会让 GPU 填充率成为瓶颈。
  4. 文本/图像质量：层被放大时纹理先栅格化后缩放，文字发虚；某些浏览器对非整数位移也会产生模糊。

因此正确的心智模型是：给"正在持续动画且内容不变"的元素提升一层，动画结束就撤掉。而不是给所有元素加 will-change 求心安——那是把预算一次性花光。

2.1 合成层提升的常见触发条件 ​

2.2 will-change 的正确用法：提前、精准、用完即撤 ​

css
/* ✓ 精准：只声明真正要动的属性 */
.card--animating {
  will-change: transform;
}

/* ✗ 撒网：给整个列表的每一项都加 */
.list-item { will-change: transform; }   /* 60 项 = 60 层，层爆炸 */

/* ✗ 过度：声明不会变化的属性 */
.foo { will-change: width, height, color, box-shadow; }
js
// ✓ 提前声明 + 动画结束回收（以 Web Animations API 为例）
const el = document.querySelector('.card');
el.style.willChange = 'transform';        // 动画开始前
el.animate(
  [{ transform: 'translateY(0)' }, { transform: 'translateY(-8px)' }],
  { duration: 240, easing: 'ease-out', fill: 'forwards' }
).finished.then(() => {
  el.style.willChange = 'auto';           // 动画结束立刻撤掉，释放纹理
});

三条原则：

  1. 提前：在动画开始前（而不是动画第一帧）声明，让浏览器有时间分配层；will-change 写在 :hover 里基本来不及。
  2. 精准：只写会变化的属性（transform、opacity），不要写 all，更不要写一堆不会动的属性。
  3. 用完即撤：动画结束后移除（auto / 删除类），否则层会常驻。持续存在的层等于持续占显存。

2.3 contain 与 content-visibility：限制影响范围 ​

css
/* contain: 告诉浏览器"这个元素的内部变化不影响外部" */
.card {
  contain: layout paint;   /* 布局隔离 + 绘制裁剪；strict 还含 size/style */
}

/* content-visibility: 屏幕外的内容直接跳过渲染 */
.section {
  content-visibility: auto;
  contain-intrinsic-size: auto 600px;  /* 占位尺寸，防止滚动条跳动 */
}
值作用
contain: layout内部布局不影响外部，外部也不影响内部
contain: paint子元素绘制被裁剪在盒子内，溢出不可见
contain: size元素尺寸不受内容影响（需显式尺寸）
contain: strict等价于 size layout paint style
content-visibility: hidden内容不渲染，但仍保留布局盒（可被 content-visibility 查询命中）
content-visibility: auto视口外跳过渲染，接近视口时自动恢复；必须配 contain-intrinsic-size

content-visibility: auto 是中长页面（文档、信息流、报表）性价比最高的优化之一：屏幕外的子树不参与布局与绘制，滚动到附近才"现算"。但它不能替代虚拟列表：DOM 节点仍然存在，内存与解析成本还在。

2.4 filter / backdrop-filter / mix-blend-mode / 大模糊的绘制成本 ​

css
/* 单层滤镜：元素自己被离屏处理后再合成 */
.thumb { filter: blur(12px) saturate(1.2); }

/* 背景滤镜：每一帧都要读取"背后已绘制的内容"再模糊 */
.glass {
  backdrop-filter: blur(20px);
  background: rgba(255, 255, 255, 0.35);
}

/* 混合模式：需要读取背景像素参与混合 */
.blend { mix-blend-mode: overlay; isolation: isolate; } /* isolate 限制混合范围 */

成本排序（同一面积、同一模糊半径下的经验值）：

text
无滤镜 < filter: blur(小) < mix-blend-mode < backdrop-filter: blur(大)

原因：

  • filter 把元素先画进离屏缓冲，再做卷积；模糊半径与面积越大，采样次数越多。
  • backdrop-filter 还要读取背景并随背景变化重算，在滚动/背景动画时几乎每帧都要重做，是低端机掉帧的重灾区。
  • mix-blend-mode 需要背景像素参与运算，且会打断某些快速合成路径；用 isolation: isolate 把混合限制在局部，能减少波及面积。
  • 大模糊（blur(40px) 以上）+ 大面积（半屏）是"绘制成本炸弹"，移动端尤其明显。参考 阴影效果 中关于大模糊与 backdrop-filter 的踩坑。

2.5 DevTools 操作指引 ​

  1. Layers 面板：More tools → Layers（Chrome）。可看到层树、每层的尺寸、内存估算、以及 "Why this layer?" 的成因；点击层可在页面上高亮。
  2. Rendering 面板：More tools → Rendering，勾选：
    • Layer borders：给每个合成层画边框，层数一目了然；
    • Paint flashing：绿色闪烁区域表示发生重绘，动画期间大面积闪烁即绘制过重；
    • Frame Rendering Stats：显示实时 FPS、GPU 内存等；
    • Show scrolling bottleneck / Show potential scroll bottlenecks：定位滚动性能问题。
  3. Performance 面板：录制动画，观察是否有 Layout / Paint 条；若只有 Composite，说明动画已交给合成器。
  4. CPU Throttling：在 Performance 面板设置 4×/6× 降速，模拟中低端手机，层与绘制的代价会被放大。

4. 使用场景示例 ​

4.1 场景一：hover 抬升动画的"提前成层 + 结束回收" ​

场景描述：卡片悬停上浮 6px，动画 240ms；列表有几十张卡，不能给每张卡常驻 will-change。

css
.card {
  transition: transform 240ms cubic-bezier(0.22, 1, 0.36, 1);
}
.card:hover { transform: translateY(-6px); }
js
// 只在指针进入的那一刻提升当前卡片，离开/动画结束立即回收
card.addEventListener('pointerenter', () => {
  card.style.willChange = 'transform';
});
card.addEventListener('transitionend', () => {
  card.style.willChange = 'auto';
});

预期效果：同一时刻最多只有一张卡成层，动画走合成器；鼠标移开后层被释放，列表滚动时不会背着几十层。

4.2 场景二：玻璃拟态面板的成本控制 ​

场景描述：中后台顶栏使用 backdrop-filter: blur(18px)，滚动时页面背景变化，面板需要每帧重算模糊。

css
.topbar {
  position: sticky;
  top: 0;
  background: rgba(255, 255, 255, 0.72);
  backdrop-filter: blur(18px);
  /* 只在支持且非低端设备时启用；否则退化为半透明纯色 */
}
@media (prefers-reduced-transparency: reduce) {
  .topbar { backdrop-filter: none; background: #fff; }
}

优化点：

  • 模糊半径控制在 12~20px，面板高度不超过一屏的 10%；
  • 滚动期间避免在面板下方做大面积图片动画；
  • 提供降级：@supports (backdrop-filter: blur(1px)) 才启用，否则用不透明背景。

4.3 场景三：长文档/报表的 content-visibility ​

场景描述：一篇 200 屏的技术文档，每屏都有代码块、表格、内联 SVG。首屏之外的布局与绘制完全可以延后。

css
.doc-section {
  content-visibility: auto;
  contain-intrinsic-size: auto 720px;  /* 估算高度，稳定滚动条 */
}

预期效果：首屏只渲染 1~2 个 section，滚动到附近才计算后续内容；大幅降低初始布局与绘制时间。注意：屏幕外内容若被搜索/打印/Ctrl+F 命中，部分浏览器会强制渲染，属预期行为。

4.4 场景四：视频/Canvas 覆盖层与层边界 ​

场景描述：播放页有视频层 + 弹幕层 + 控制栏。视频天然成层，弹幕若每帧改 top 会触发主线程布局。

css
.video   { will-change: transform; }        /* 视频层：播放期间保持 */
.danmaku { transform: translate3d(0, 0, 0); } /* 弹幕层：用合成器移动 */

优化点：

  • 弹幕位置用 transform: translateX() 驱动，不要改 left；
  • 弹幕层数量设上限（例如同屏 50 条），超出复用池；
  • 视频与弹幕之间避免不必要的 backdrop-filter/mix-blend-mode，否则每帧都要读回视频帧。

4.5 场景五：层检查——用数据而不是感觉判断 ​

js
// 粗略估算某个元素的层显存（仅作教学/自检，真实值看 DevTools Layers）
function estimateLayerBytes(el) {
  const rect = el.getBoundingClientRect();
  const dpr = window.devicePixelRatio || 1;
  return rect.width * rect.height * dpr * dpr * 4;
}

预期效果：给一个 400×300 的卡片在 DPR 2 下算出约 1.83MB；60 张卡就是 110MB 量级——这时你会立刻明白"全部加 will-change"为什么危险。实际层数与内存请以 Layers 面板为准，本函数只用于建立数量级直觉。

5. 实际应用案例分析 ​

5.1 案例一：移动端列表"全部 will-change"导致 iOS 白屏 ​

背景：某电商 H5 商品列表，开发者为"保证滚动顺滑"，给每个商品卡加 will-change: transform，首屏 20 张、整页 200+ 张。

现象：iPhone 8/SE 等 2GB 内存机型上，滑到第 3 屏后页面白屏、Safari 提示"此网页重新加载"；低端安卓则明显掉帧。

定位：Layers 面板显示 200+ 个合成层，单层约 1~3MB，总显存估算超过 200MB；系统在内存压力下回收 WebProcess 的 GPU 资源，触发页面重载。该现象与 阴影效果 案例中记录的"60 卡 will-change 白屏"一致。

修复：

  1. 移除列表项上的常驻 will-change；
  2. 只给"滚动容器"一个层，让子元素共享合成结果；
  3. 卡片 hover/按压期间用 pointerenter 临时提升，pointerleave 回收；
  4. 图片统一 decoding="async" + 固定宽高比，避免解码抖动；
  5. 用 content-visibility: auto 跳过屏幕外楼层。

结果：层数从 200+ 降到个位数，显存回落到 20MB 以内，白屏消失，滚动帧率恢复。

5.2 案例二：中后台玻璃面板 + 大模糊导致滚动掉帧 ​

背景：某 SaaS 控制台顶栏与侧栏使用 backdrop-filter: blur(24px)，背景是动态渐变。用户反馈"滚动时像幻灯片"。

定位：Rendering 面板开 Paint flashing，滚动时整个顶栏区域持续绿色闪烁；Performance 面板显示每帧都有长条 Paint，主线程与 GPU 同时吃满。原因是背景渐变在动，backdrop-filter 每帧都要重新采样背景并做卷积。

修复：

  1. 模糊半径从 24px 降到 14px；
  2. 顶栏下方停止动态渐变，改为静态纹理；
  3. 滚动期间用 will-change: transform 提升顶栏，减少重绘触发；
  4. 低端设备通过 @supports + 运行时设备判断关闭模糊，退化为 90% 不透明背景。

结果：滚动帧率从 24~30fps 提升到 55~60fps，GPU 占用下降约一半（团队内部测量）。

5.3 案例三：translateZ(0) 祖传代码的清理 ​

背景：老项目里到处是 transform: translateZ(0)，据说是"开启硬件加速、修复 iOS 闪烁"。

分析：该写法源于 iOS Safari 6 时代——当时 3D 变换能避免某些滚动重绘与文字闪烁。现代浏览器已修复相关问题，而这段代码仍在制造大量不必要的层：一个 100 行的表格，每行都有 translateZ(0)，等于 100 个层。

处理：

  1. 用代码搜索统计 translateZ(0) / translate3d(0,0,0) 出现位置；
  2. 逐处用 Layers 面板验证"去掉后是否仍流畅"；
  3. 仅保留真正需要独立变换的层（如视频、轮播、拖拽层）；
  4. 统一替换为"按需 will-change + 动画结束回收"的模式。

结论：translateZ(0) 不是禁用词，但它应该是有明确理由的局部手段，而不是全局默认值。历史包袱要清，不要复制。

6. 最佳实践与常见坑 ​

  1. 先测量再提升：用 Layers 面板确认元素是否已成层、层数是否合理；不要凭"加了 translateZ(0) 就快"的直觉改代码。
  2. 只给正在动的元素提升：will-change 的生命周期应覆盖动画本身，动画结束立即置回 auto；常驻声明等于常驻显存。
  3. 精准声明属性：will-change: transform, opacity 足够；禁止 will-change: all，也不要声明不会变化的 width/height/color。
  4. 不要给列表每一项加层：60 张卡各自成层是典型的层爆炸；优先给滚动容器/动画容器提升一次，子元素共享。
  5. translateZ(0) 要有理由：只在需要独立 3D/合成行为时使用；清理祖传的全局 translateZ(0)。
  6. 大模糊是预算黑洞：filter: blur()、backdrop-filter、mix-blend-mode 大面积使用时，先降半径、再降面积、最后才考虑关闭。
  7. 用 isolation: isolate 收口混合：mix-blend-mode 的作用范围越小，需要读取的背景像素越少。
  8. 层尺寸按设备像素算：估算显存用 宽 × 高 × DPR² × 4；高分屏下同一元素的层是 DPR 1 的 4 倍。
  9. 长页面先上 content-visibility：屏幕外内容跳过布局/绘制，配 contain-intrinsic-size 防滚动条抖动；虚拟列表解决 DOM 数量，二者互补。
  10. contain: paint 配合滚动容器：裁剪溢出、限制重绘范围；但注意它会影响 position: fixed 子元素的包含块与 3D 打平行为。
  11. 动画期间避免改变层内容：层内文字/图片变化会触发重新栅格化；能预渲染就预渲染，能复用就复用。
  12. 在低端设备上验证：DevTools CPU 4×/6× 节流 + 真机测试；桌面浏览器的高配 GPU 很容易掩盖层爆炸的代价。
  13. 页面不可见时暂停动画：visibilitychange 时暂停持续动画，减少 GPU/电量消耗，也避免切回时的"追帧"。
