CSS/HTML 反例库：30 个典型错误写法与修复 ​

面向已能写页面、但想减少返工的前端开发者 —— 反例的价值不在「记住不要这样写」，而在看清「这样写会触发哪条机制、导致什么后果」。每条反例都按「错法 → 修法 → 机制」组织，便于在代码评审中直接对照。

1. 概念解释 ​

1.1 反例的记忆优势 ​

正例告诉你「可以这样」，反例告诉你「这样会坏，而且坏在哪」。错误往往由多个机制叠加产生：margin 折叠、min-width: auto、包含块选择、层叠顺序。只看结论记不住，看到因果才能迁移。

1.2 三类错误 ​

类型特征修复方向
语义错误能用但读屏 / 键盘不可用换原生元素、补名称
机制误用在特定条件下才坏理解包含块、格式化上下文、层叠
工程债当下能跑，长期失控令牌、层、预算、测试

1.3 反例库的用法 ​

评审时按类别扫一遍；出现线上问题时先归类，再定位机制。不要试图一次改完 30 条，按「影响用户数 × 修复成本」排序。

2. 语法说明 —— 如何在评审中识别 ​

2.1 静态扫描 ​

bash
# 常见可疑写法
rg -n "outline:\s*none|transition:\s*all|z-index:\s*9999|!important" src/
rg -n "will-change" src/
rg -n "<div[^>]*on(click|keydown)" src/

2.2 评审清单 ​

  • 交互元素是否为 button / a / input？
  • 是否只有鼠标路径，没有键盘路径？
  • 固定高度 / 固定宽度是否装在可变内容上？
  • 是否有裸 !important 或超高特异性？
  • 动画是否尊重 prefers-reduced-motion？
  • 图片是否声明尺寸，避免 CLS？

2.3 运行时检查 ​

js
// 找出不可聚焦但绑定了点击的元素
[...document.querySelectorAll("[onclick]")]
  .filter((el) => !el.matches("button, a[href]") && !el.hasAttribute("tabindex"));

3. 浏览器兼容性 ​

反例库中的问题大多与浏览器无关，而是与规范行为有关：

  • margin 折叠、min-width: auto、包含块规则在各引擎一致。
  • 100vh 在移动端受动态工具栏影响，各移动浏览器表现不同。
  • transition: all 在不同引擎对可动画属性的覆盖略有差异。
  • :focus-visible 需 Safari 15.4+，旧版可用 :focus 兜底。

4. 三十条反例与修复 ​

A. 语义与可访问性 ​

01 · 用 div 当按钮

html
<!-- ❌ 不可聚焦、无角色、回车不触发 -->
<div class="btn" onclick="save()">保存</div>
<!-- ✅ -->
<button type="button" onclick="save()">保存</button>

机制：原生 button 自带按钮角色、Tab 焦点与 Enter / Space 激活；div 三样都要手写，通常漏掉。

02 · 图标按钮没有可访问名称

html
<!-- ❌ 读屏只念「按钮」 -->
<button>✕</button>
<!-- ✅ -->
<button aria-label="关闭对话框">✕</button>

机制：可访问名称来自内容或 aria-label；纯符号无法表达意图。

03 · 移除焦点轮廓

css
/* ❌ 键盘用户丢失位置 */
:focus { outline: none; }
/* ✅ */
:focus-visible { outline: 2px solid #2563eb; outline-offset: 2px; }

机制：:focus-visible 由浏览器判断「是否需要可见焦点」，鼠标点击不显示，键盘导航显示。

04 · 图片缺少替代文本

html
<!-- ❌ -->
<img src="chart.png">
<!-- ✅ 有信息 -->
<img src="chart.png" alt="季度营收环比增长 12%">
<!-- ✅ 纯装饰 -->
<img src="divider.png" alt="">

机制：读屏通过 alt 决定播报内容；缺省时可能读出文件名，纯装饰则应显式空字符串。

05 · 标题层级跳级 / 多个 h1

html
<!-- ❌ 从 h1 直接到 h3 -->
<h1>订单</h1><h3>筛选</h3>
<!-- ✅ -->
<h1>订单</h1><h2>筛选</h2>

机制：读屏用户靠标题列表跳转，跳级破坏层级心智模型。

B. 布局 ​

06 · 用固定高度装可变内容

css
/* ❌ 内容一多就溢出或截断 */
.card { height: 120px; overflow: hidden; }
/* ✅ */
.card { min-height: 120px; }

机制：height 是硬约束，内容超出会被裁剪；min-height 只设下限，可随内容增长。

07 · 用 margin 做间隔，遇到折叠

css
/* ❌ 相邻块 margin 折叠，间距小于预期 */
.item { margin-bottom: 20px; }
/* ✅ */
.list { display: grid; gap: 20px; }

机制：普通流中相邻块的外边距会折叠，取较大值；gap 由布局容器分配，不参与折叠。

08 · Flex 子项不收缩，长文本撑破

css
/* ❌ 子项 min-width:auto，长单词撑破容器 */
.row { display: flex; }
.title { flex: 1; }
/* ✅ */
.title { flex: 1; min-width: 0; overflow: hidden; text-overflow: ellipsis; }

机制：Flex 子项默认 min-width: auto，不会小于内容最小宽度；显式 min-width: 0 才允许收缩。

09 · absolute 找不到定位祖先

css
/* ❌ 祖先都没定位，元素相对初始包含块定位 */
.badge { position: absolute; top: 8px; right: 8px; }
/* ✅ */
.card { position: relative; }

机制：绝对定位的包含块是最近的非 static 祖先；没有则退到初始包含块，位置完全失控。

10 · 用 float 做整体布局

css
/* ❌ 需要清除浮动，高度塌陷 */
.col { float: left; width: 33.33%; }
/* ✅ */
.layout { display: grid; grid-template-columns: repeat(3, 1fr); }

机制：浮动元素脱离普通流，父容器不计算其高度；Grid / Flex 是正规的布局上下文。

11 · 用 100vh 做移动端全屏

css
/* ❌ 移动端地址栏收起时内容被遮挡 */
.hero { height: 100vh; }
/* ✅ */
.hero { min-height: 100svh; }

机制：vh 基于最大视口，移动端工具栏会变化；svh 基于最小视口，内容始终可见。

C. 层叠与选择器 ​

12 · 靠 !important 覆盖

css
/* ❌ 逼后来者继续加 !important */
.btn { color: red !important; }
/* ✅ 用层或提高语义化选择器 */
@layer components { .btn { color: var(--color-danger); } }

机制：!important 改变层叠顺序，形成不可控的连锁；@layer 让顺序显式可管。

13 · 特异性军备竞赛

css
/* ❌ 越写越长 */
.page .card .btn.btn--primary { color: blue; }
/* ✅ */
@layer components { .btn--primary { color: blue; } }

机制：分层后先比层顺序，再比特异性；层级秩序替代了选择器长度。

14 · z-index: 9999

css
/* ❌ 下一个弹窗只能写 99999 */
.modal { z-index: 9999; }
/* ✅ 用令牌分层 */
:root { --z-modal: 100; --z-toast: 200; }

机制：z-index 只在同一层叠上下文中比较；乱写数字会掩盖「谁创建了层叠上下文」这个真问题。

15 · 过度全局重置

css
/* ❌ 抹掉所有默认样式，表单与列表可用性下降 */
* { margin: 0; padding: 0; list-style: none; }
/* ✅ 按需重置 */
*, *::before, *::after { box-sizing: border-box; }

机制：全局重置会移除浏览器提供的可用默认值（如列表语义、表单控件外观），需逐项确认。

16 · 用 ID 写样式

css
/* ❌ 特异性 1-0-0，后续只能加 !important */
#header .nav { color: #fff; }
/* ✅ */
.nav--dark { color: #fff; }

机制：ID 特异性极高，组件复用时几乎无法覆盖。

D. 视觉与动效 ​

17 · transition: all

css
/* ❌ 布局属性也被动画，引发重排 */
.card { transition: all .3s; }
/* ✅ */
.card { transition: transform .3s, opacity .3s; }

机制：all 会监听所有可动画属性；width、top 等触发布局，代价高且容易产生意外动画。

18 · 只做 :hover，不做 :focus-visible

css
/* ❌ 键盘用户看不到反馈 */
.btn:hover { background: #1d4ed8; }
/* ✅ */
.btn:hover, .btn:focus-visible { background: #1d4ed8; }

机制：悬停与键盘焦点是两条独立路径，视觉反馈要成对提供。

19 · 动画不尊重减弱动效偏好

css
/* ❌ 前庭敏感用户被迫看大幅动画 */
.hero { animation: slide 1s infinite; }
/* ✅ */
@media (prefers-reduced-motion: reduce) {
  .hero { animation: none; }
}

机制：系统级偏好是用户明确表达的可访问性需求，应作为一等条件。

20 · 浅灰文字对比度不足

css
/* ❌ 白底上约 1.9:1 */
.muted { color: #b6c2d1; }
/* ✅ 约 4.7:1 */
.muted { color: #64748b; }

机制：正文对比度要求 4.5:1；低对比在强光、低质量屏幕下不可读。

21 · 用图片做文字

html
<!-- ❌ 不可选中、不可缩放、读屏无内容 -->
<img src="title.png" alt="">
<!-- ✅ -->
<h2>季度报告</h2>

机制：文本图片失去文本的全部能力：选择、搜索、缩放、读屏、翻译。

E. 性能 ​

22 · 布局抖动（读写交替）

js
// ❌ 每次循环都强制同步布局
items.forEach((el) => {
  el.style.width = "24px";
  console.log(el.offsetWidth);
});
// ✅ 先读后写
const widths = items.map((el) => el.offsetWidth);
items.forEach((el, i) => { el.style.width = widths[i] + "px"; });

机制：写样式会使布局失效，紧接着读几何属性会强制浏览器同步重排。

23 · will-change 常驻

css
/* ❌ 长期占层，内存与合成成本上升 */
.card { will-change: transform; }
/* ✅ 交互前临时加，结束后移除 */
.card:hover { will-change: transform; }

机制：will-change 提前创建合成层；大量常驻会导致层爆炸与内存压力。

24 · 图片不设尺寸导致 CLS

html
<!-- ❌ 加载后撑开布局 -->
<img src="hero.jpg">
<!-- ✅ -->
<img src="hero.jpg" width="800" height="450" alt="">

机制：浏览器用宽高比预留空间；没有尺寸时，图片加载完成会触发布局偏移。

25 · 同步加载第三方脚本

html
<!-- ❌ 阻塞解析与渲染 -->
<script src="https://cdn.example/analytics.js"></script>
<!-- ✅ -->
<script src="https://cdn.example/analytics.js" defer></script>

机制：普通脚本阻塞 HTML 解析；defer 延后到解析完成，async 适合独立脚本。

26 · 长列表一次性渲染

js
// ❌ 一万个节点，主线程长时间阻塞
list.innerHTML = items.map(render).join("");
// ✅ 分片或虚拟列表
const chunk = items.slice(0, 50);
requestAnimationFrame(() => renderChunk(chunk));

机制：大量 DOM 创建与布局在同一任务内完成，会形成长任务，阻塞输入响应。

F. 工程与兼容 ​

27 · 直接改第三方库源码

text
❌ node_modules 里改一行
✅ 用受支持的扩展点，或 fork 后锁定版本

机制：依赖重装会覆盖改动，团队无法复现；补丁必须有版本与升级路径。

28 · 魔法数字散落

css
/* ❌ 同一个间距出现 13px / 14px / 15px */
.card { padding: 13px; }
/* ✅ */
.card { padding: var(--space-3); }

机制：没有单一来源，主题与密度调整无法统一；令牌把值收敛到一处。

29 · 只测最新 Chrome

text
❌ 开发机最新版通过就发布
✅ 兼容矩阵 + 旧引擎冒烟 + 强制降级用例

机制：新特性在旧引擎可能整段失效；渐进增强与兜底路径需要被测试，否则会腐坏。

30 · 用 UA 判断能力

js
// ❌ UA 会伪装、会过期
if (/Chrome/.test(navigator.userAgent)) { enablePopover(); }
// ✅
if ("popover" in HTMLElement.prototype) { enablePopover(); }

机制：能力检测直接问「这个 API 在不在」，UA 判断问的是「你是谁」，两者语义不同。

5. 实际应用案例分析 ​

背景：某后台页面在评审中被指出 14 个问题，团队按「影响面 × 成本」排序，一周内修完 9 个高优先级项。

修复顺序：

  1. div 假按钮与图标按钮无名称（影响所有键盘 / 读屏用户）；
  2. 移除 outline 与浅灰文字对比度（影响可达性验收）；
  3. min-width: 0 导致的文本撑破（影响移动端布局）；
  4. transition: all 与布局抖动（影响低端机流畅度）；
  5. 图片尺寸与第三方脚本加载方式（影响 CLS 与首屏）。

结果：键盘任务完成率从 72% 升到 100%，移动端横向溢出归零，首屏 CLS 从 0.21 降到 0.04。剩余 5 项（如 z-index 治理、魔法数字）进入架构篇的令牌与层叠改造。

6. 最佳实践与常见坑 ​

  1. 先修影响用户的：语义与可访问性优先于代码风格。
  2. 一次只改一类：把语义、布局、性能分开提交，便于回滚与验证。
  3. 用机制解释而非口号：评审意见写清「触发了哪条规则」。
  4. 把反例变成检查：lint 规则、审计脚本、CI 门禁比记忆可靠。
  5. 不要为反例而反例：!important 在极少数边界场景仍可使用，但要写清原因。
  6. 修复要配验证：每条修复都应有可复现的前后对比或测试。
