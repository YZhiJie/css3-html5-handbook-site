性能预算与 CI 门禁 ​

面向性能工程与前端架构人员的预算治理参考资料 —— 性能预算不是「定一个数字」，而是把「可接受的最差体验」翻译成资源体积、请求数与指标阈值，再接到 CI 上让超支无法合入。

配套可运行示例（单文件 HTML，双击即开）：

示例文件演示内容
index-01-performance-budget.html调整 JS / CSS / 图片体积与请求数，实时估算传输体积与指标并对照预算判定通过 / 失败；另有真实长任务测量按钮，用 PerformanceObserver 验证「超过 50ms 即长任务」

1. 概念解释 ​

1.1 预算的三层 ​

层级例子作用
资源预算首屏 JS ≤ 170KB、图片 ≤ 300KB约束「交付物」
请求预算关键请求 ≤ 12 个、第三方域 ≤ 2 个约束「连接成本」
指标预算LCP ≤ 2.5s、CLS ≤ 0.1、INP ≤ 200ms约束「用户感受」

因果关系：资源与请求是可归因的输入，指标是最终输出。只定指标，超支时不知道是谁超的；只定资源，可能省了字节却仍然慢。

1.2 为什么必须进 CI ​

预算写在文档里没有约束力。只有变成流水线断言，「超支」才会在合入前暴露，而不是在线上被用户发现。

1.3 预算不是越低越好 ​

过度收紧会让团队为了数字牺牲功能，最终绕过门禁。合理做法是：先用真实用户数据（RUM）确定分位值，再取 P75 作为目标，留出波动余量。

1.4 波动与噪声 ​

指标受设备、网络、缓存影响。CI 环境应固定设备档位与网络模型，并允许合理波动区间；否则门禁会变成随机失败源。

2. 语法说明 ​

2.1 预算文件 ​

json
{
  "resource": {
    "js": 170,
    "css": 50,
    "image": 300,
    "font": 80,
    "total": 600
  },
  "requests": { "critical": 12, "thirdParty": 2 },
  "metrics": { "lcp": 2500, "cls": 0.1, "inp": 200, "tbt": 300 }
}

单位要写清楚：体积用 KB（未压缩 / 压缩后需注明），指标用毫秒。

2.2 构建产物断言 ​

js
// 统计首屏 chunk 体积，超过即失败
const budget = 170 * 1024;
const bytes = fs.statSync("dist/assets/index.js").size;
if (bytes > budget) {
  console.error(`首屏 JS ${(bytes / 1024).toFixed(1)}KB > 预算 170KB`);
  process.exit(1);
}

2.3 实验室指标采集 ​

js
new PerformanceObserver((list) => {
  for (const entry of list.getEntries()) {
    if (entry.entryType === "largest-contentful-paint") {
      console.log("LCP", entry.startTime);
    }
    if (entry.entryType === "layout-shift" && !entry.hadRecentInput) {
      cls += entry.value;
    }
  }
}).observe({ type: "largest-contentful-paint", buffered: true });

2.4 长任务观测 ​

js
new PerformanceObserver((list) => {
  for (const entry of list.getEntries()) {
    console.warn("长任务", entry.duration.toFixed(1), "ms");
  }
}).observe({ type: "longtask", buffered: true });

超过 50ms 的任务会阻塞输入响应；预算通常看 TBT（总阻塞时间）。

2.5 门禁分级 ​

js
const level = overBy > 0.2 ? "error" : overBy > 0 ? "warn" : "pass";

小幅超支先告警，显著超支直接阻断，避免「一刀切」导致流程僵化。

3. 浏览器兼容性 ​

  • PerformanceObserver：Chrome 52+、Firefox 57+、Safari 11+。
  • LCP / CLS：Chrome 77+、Safari 14.1+、Firefox 89+。
  • INP：Chrome 96+ 起可观测；其他引擎支持逐步完善。
  • longtask：Chromium 系支持较好；跨浏览器可用 TBT 近似。
  • Resource Timing：现代浏览器均支持，需注意跨域资源的 Timing-Allow-Origin。

4. 使用场景示例 ​

场景 1：首屏 JS 预算 ​

把路由级 chunk 与公共依赖分开统计，首屏只计入真正阻塞渲染的部分；懒加载模块不计入首屏预算，但计入总量。

场景 2：图片预算 ​

按视口宽度生成响应式图，首屏图限制单张体积；用 loading="lazy" 把非首屏图片移出关键路径。

场景 3：第三方门禁 ​

限制第三方脚本域名与数量，并对每个第三方设定独立预算；一个统计 SDK 不应吃掉全部额度。

场景 4：PR 评论 ​

CI 把「本次 vs 基线」的体积变化贴到 PR：

text
首屏 JS: 148.2KB → 176.4KB (+28.2KB, +19%) ❌ 超出 170KB 预算

变化量与归因比一个红叉更有用。

5. 实际应用案例分析 ​

背景：某内容站 LCP 从 2.1s 恶化到 4.3s，排查发现首屏 JS 从 160KB 涨到 340KB，但没有任何 CI 检查。

根因：

  1. 依赖升级引入整包 lodash；
  2. 首屏同步加载了图表库；
  3. 没有体积预算，PR 无法感知；
  4. 指标只看线上，发现时已过两周。

修复：

  1. 建立三层预算，写入仓库根目录；
  2. 构建后统计 chunk，超预算阻断合并；
  3. 图表库改为动态 import()，移出首屏；
  4. lodash 改为按需导入；
  5. CI 固定网络与设备档位，跑实验室指标并贴 PR 评论。

结果：首屏 JS 回落到 165KB，LCP 回到 2.2s；后续三个月拦截了 7 次体积回退。收益来自「让超支在合入前可见」。

6. 最佳实践与常见坑 ​

  1. 三层预算成组：资源、请求、指标都要有，单看一层会漏。
  2. 单位与口径写清：压缩前 / 压缩后、KB / KiB、实验室 / 现场，避免争议。
  3. 用 P75 定目标：不要用平均值，也不要拍脑袋取极限值。
  4. 分级门禁：小幅超支告警、显著超支阻断，保留合理弹性。
  5. 归因到 PR：输出变化量与超支模块，比只报失败更有行动力。
  6. 固定 CI 环境：设备、网络、缓存策略一致，减少噪声。
  7. 预算要复查：业务变化后定期校准，过期预算会逼团队绕过门禁。
